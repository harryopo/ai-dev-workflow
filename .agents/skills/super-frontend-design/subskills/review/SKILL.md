### 1. 概述

设计审查子技能是 super-frontend-design 的核心质量保障模块，负责对现有界面进行全方位 UI/UX 质量审查，并提供可执行的改进建议。

**审查定位：**
- 全方位 UI/UX 质量审查，不仅仅是视觉检查
- 从用户视角出发，覆盖从视觉呈现到交互体验的完整链路
- 输出结构化审查报告，包含具体改进建议和优先级排序
- **必须对照 Design Brief 验证设计是否满足用户原始需求**

**适用场景：**
- 网站（营销站、内容站、电商站）
- 落地页（Landing Page）
- 仪表板（Dashboard）
- 产品 UI（SaaS 应用、管理后台）
- 应用壳（App Shell）
- 组件（按钮、表单、卡片、表格等）
- 表单（注册、登录、设置等）
- 设置页面
- 引导流程（Onboarding）
- 空状态页面

**核心能力：**
- 19 个审查维度，覆盖 UI/UX 全部关键领域
- 每个维度包含具体检查项和量化标准
- 问题标记采用三级严重度（高/中/低）
- 审查后可直接执行改进，形成闭环

**基于 impeccable 重新实现：**
- 保留了 impeccable 的全面审查维度
- 增加了量化评分体系（0-100分）
- 增加了结构化报告格式
- 增加了改进执行闭环

### §0. 调研守卫（在一切审查之前）

> 🚫 **如果用户的真实意图是"优化/改进/美化/重新设计"已有网页，而非纯审查 → 立即停止，回退到 research 子技能。**

**判断标准**（满足任一即回退）：
1. 用户说"优化/改进/美化/改造/升级/重新设计"而非"审查/检查/评分"
2. 用户对现有设计不满意，想要换风格/换配色/换布局
3. 没有 Design Brief（说明没走过调研流程）

**回退动作**：告知用户"您需要的是重新设计而非审查，我将先进行需求调研"，然后加载 `subskills/research/SKILL.md` 启动 AskUserQuestion 调研对话。

> ⚠️ **review 只做"诊断"不做"治疗"。** 如果用户要治疗（改变设计），那不是 review 的工作。

### 0. 审查前置：设计灵魂追溯（Design Brief 对照验证）

> ⚠️ **在执行 19 维度技术审查之前，必须先验证设计是否符合用户原始需求。**

#### 检查表（必须逐项确认）

| # | 检查项 | 验证方式 | 不合格处理 |
|:---:|------|---------|-----------|
| 1 | **品牌人格体现** | 设计是否让用户感受到 Design Brief 中指定的品牌人格？ | 🔴 严重：设计方向错误，需重新设计 |
| 2 | **情绪板匹配** | 3 个关键词是否在视觉中体现？（如"科技感+未来感+冷静"） | 🔴 严重：情绪不对，调整配色/材质 |
| 3 | **视觉论文一致性** | 最终产出是否与 creative 阶段的 5 个方向决策一致？ | 🟡 中等：标注偏差并建议修正 |
| 4 | **设计禁忌合规** | 逐项检查用户列出的所有设计禁忌是否被违反？ | 🔴 严重：违禁出现，必须移除 |
| 5 | **企业参考风格** | 是否体现了用户选择的企业参考风格特征？ | 🟡 中等：标注缺失 |
| 6 | **响应式与设计类型一致** | 设计类型是后台 → 检查信息密度；是落地页 → 检查视觉冲击 | 🔴 严重：类型不匹配需重设计 |
| 7 | **暗色模式与调研一致** | 用户说要暗色 → 必须检查暗色实现；用户说不要 → 不应出现 | 🟡 中等 |
| 8 | **交互复杂度与调研一致** | 用户说静态展示 → 不应有复杂交互；用户说完整应用 → 必须有路由/状态管理 | 🟡 中等 |

#### 全局画像禁令

- ❌ 不从用户全局画像中读取偏好看设计是否"符合"
- ❌ 不因为"用户上次喜欢暗色"就判定当前亮色设计不合格
- ✅ 审查的「期望」只能来自 Design Brief 和本次会话上下文

#### 设计灵魂评分

基于以上 8 项检查，给出设计灵魂匹配度评分（0-100分）：

| 得分 | 等级 | 说明 |
|:---:|:---:|------|
| 90-100 | A+ | 完美体现用户所有调研需求 |
| 75-89 | A | 基本满足，有少量偏差 |
| 60-74 | B | 存在明显偏差，需要调整 |
| <60 | C | 设计方向与调研结果严重不符，建议重新设计 |

### 2. 审查维度（完整列出所有维度）

#### 2.1 视觉审查

视觉审查关注界面的视觉呈现质量，确保信息能够有效地通过视觉传递给用户。

**2.1.1 视觉层次**

检查项：
- 是否有清晰的视觉层次？最重要的元素是否最突出？
- 标题是否比正文更大更粗？
- CTA 按钮是否比普通按钮更醒目？
- 关键信息是否通过大小、颜色、位置建立了明确的优先级？
- 是否存在视觉竞争（多个元素争夺注意力）？

量化标准：
- 标题与正文字号比应 ≥ 1.5:1
- CTA 按钮与普通按钮面积比应 ≥ 1.3:1
- 首屏应有且仅有 1 个最突出的视觉焦点

**2.1.2 信息架构**

检查项：
- 内容是否按逻辑组织？用户能否快速找到所需信息？
- 导航结构是否清晰？层级是否不超过 3 层？
- 相关内容是否分组？不相关内容是否分离？
- 是否遵循了 F 型或 Z 型阅读模式？
- 信息密度是否适当？

量化标准：
- 导航层级 ≤ 3 层
- 每个分组包含 3-7 个项目（Miller's Law）
- 首屏可见的核心操作 ≤ 5 个

**2.1.3 认知负荷**

检查项：
- 界面是否过于复杂？是否需要简化？
- 用户完成核心任务需要多少步骤？
- 是否有不必要的决策点？
- 是否利用了渐进式披露（Progressive Disclosure）？
- 信息是否分块呈现？

量化标准：
- 核心任务完成步骤 ≤ 5 步
- 同一屏幕的决策选项 ≤ 7 个
- 表单字段数 ≤ 核心所需 + 2

---

#### 2.2 可访问性审查

可访问性审查确保界面对所有用户可用，包括残障用户。

**2.2.1 对比度**

检查项：
- 文本对比度是否满足 WCAG AA（4.5:1）？
- 大文本（≥18pt 或 ≥14pt 粗体）对比度是否满足 3:1？
- 非文本元素（图标、边框）对比度是否满足 3:1？
- 暗色模式下的对比度是否独立验证？

量化标准：
- 正文文本对比度 ≥ 4.5:1（WCAG AA）
- 大文本对比度 ≥ 3:1（WCAG AA）
- 建议达到 WCAG AAA 标准（正文 ≥ 7:1）

**2.2.2 键盘导航**

检查项：
- 是否支持完整的键盘导航？
- Tab 顺序是否符合逻辑？
- 是否有键盘陷阱（Keyboard Trap）？
- 焦点是否可见且明显？
- 是否支持快捷键？

量化标准：
- 所有交互元素可通过键盘访问
- 焦点环对比度 ≥ 3:1
- 无键盘陷阱

**2.2.3 屏幕阅读器**

检查项：
- 是否有适当的 ARIA 标签？
- 图片是否有 alt 文本？
- 表单是否有关联的 label？
- 动态内容是否有 aria-live 区域？
- 页面结构是否使用语义化 HTML？

量化标准：
- 所有 `<img>` 有非空 alt 或 `alt=""`
- 所有 `<input>` 有关联 `<label>` 或 `aria-label`
- 使用 `<nav>`、`<main>`、`<aside>`、`<footer>` 等语义标签

**2.2.4 颜色依赖**

检查项：
- 是否仅靠颜色传达信息？
- 错误状态是否同时使用图标/文本和颜色？
- 链接是否通过下划线或背景区分（不仅仅是颜色）？
- 图表是否使用形状/图案辅助颜色区分？

量化标准：
- 无任何信息仅通过颜色传达
- 错误状态至少使用颜色 + 图标/文本双重编码

#### 2.3 性能审查

性能审查关注界面的加载和运行时性能，确保用户体验流畅。

**2.3.1 图片优化**

检查项：
- 是否使用 WebP/AVIF 格式？
- 是否有响应式图片（srcset）？
- 是否有懒加载（loading="lazy"）？
- 图片尺寸是否合适（无过大图片）？
- 是否有占位符/模糊预览？

量化标准：
- 图片格式优先 WebP/AVIF
- 宽度 > 600px 的图片使用 srcset
- 非首屏图片使用 lazy loading
- 单张图片 ≤ 200KB（压缩后）

**2.3.2 字体加载**

检查项：
- 是否使用 font-display: swap？
- 是否预加载关键字体（preload）？
- 字体文件数量是否 ≤ 4 个？
- 是否有字体回退栈？

量化标准：
- 所有 @font-face 使用 font-display: swap
- 关键字体使用 `<link rel="preload">`
- 字体文件数 ≤ 4（2 字体 × 2 字重）

**2.3.3 布局稳定性**

检查项：
- 是否有 CLS（Cumulative Layout Shift）问题？
- 图片/视频是否有明确的 width/height？
- 动态内容是否有预留空间？
- 字体加载是否导致布局偏移？

量化标准：
- CLS ≤ 0.1（Good）
- 所有媒体元素有明确尺寸
- 动态内容使用 min-height 预留空间

**2.3.4 代码分割**

检查项：
- 是否按路由/功能拆分代码？
- 第三方库是否按需加载？
- CSS 是否有未使用的规则？
- JavaScript bundle 大小是否合理？

量化标准：
- 首屏 JS ≤ 100KB（压缩后）
- 路由级别代码分割
- CSS 未使用率 ≤ 20%

---

#### 2.4 响应式审查

响应式审查确保界面在不同设备和屏幕尺寸下可用。

**2.4.1 移动端优先**

检查项：
- 是否从移动端设计开始？
- 移动端布局是否独立于桌面端？
- 触摸交互是否优先考虑？
- 内容优先级是否在移动端重新排列？

量化标准：
- 移动端布局非桌面端简单缩放
- 核心内容在 320px 宽度下可访问

**2.4.2 断点一致性**

检查项：
- 是否使用系统化断点？
- 断点之间是否有布局跳跃？
- 是否覆盖所有主流设备尺寸？

量化标准：
- 使用标准断点：640px / 768px / 1024px / 1280px / 1536px
- 相邻断点间无布局跳跃

**2.4.3 触摸目标**

检查项：
- 是否满足 44×44pt 最小尺寸？
- 触摸目标之间是否有足够间距？
- 小屏幕上按钮是否足够大？

量化标准：
- 可点击元素最小尺寸 ≥ 44×44pt
- 相邻触摸目标间距 ≥ 8pt

**2.4.4 横向模式**

检查项：
- 是否在横向模式下可用？
- 横向布局是否重新排列？
- 是否有横向专属优化？

量化标准：
- 横向模式下无内容溢出或截断
- 横向模式下核心功能可用

#### 2.5 主题审查

主题审查确保界面正确使用主题系统，保持视觉一致性。

**2.5.1 暗色模式**

检查项：
- 暗色模式是否完整？所有组件是否适配？
- 暗色模式对比度是否独立验证？
- 暗色模式下图片/图标是否调整？
- 暗色模式切换是否平滑？

量化标准：
- 所有组件有暗色模式变体
- 暗色模式文本对比度 ≥ 4.5:1
- 暗色模式使用 `#1a1a1a` 左右背景而非纯黑 `#000000`

**2.5.2 语义 Token**

检查项：
- 是否使用语义 Token 而非原始 hex 值？
- 是否有硬编码的颜色值？
- Token 引用是否正确？

量化标准：
- CSS 中无硬编码 hex/rgb 值（除原始 Token 定义外）
- 所有颜色引用使用 var(--color-xxx) 格式

**2.5.3 品牌一致性**

检查项：
- 是否遵循品牌规范？
- 品牌色使用是否正确？
- 字体使用是否符合品牌指南？

量化标准：
- 品牌色使用位置和比例符合规范
- 字体配对与品牌指南一致

---

#### 2.6 排版审查

排版审查确保文本内容的可读性和视觉美感。

**2.6.1 字体配对**

检查项：
- distinct font-family 是否 ≤3，且第 3 族只承担功能性 register（`scripts/slop_scan.py` 的 `too-many-font-families` / `outlier-face-overuse` 已自动判定）？
- 标题字体和正文字体是否形成对比？
- 字体风格是否与品牌调性一致？

量化标准：
- 字体种类 ≤ 2（+1 等宽字体用于代码）
- 标题字体与正文字体有明显风格差异

**2.6.2 行高**

检查项：
- 正文行高是否在 1.5-1.75 之间？
- 标题行高是否在 1.1-1.3 之间？
- 行高是否根据字号调整？

量化标准：
- 正文行高：1.5-1.75
- 标题行高：1.1-1.3
- 小字号行高相对更大

**2.6.3 行长**

检查项：
- 是否限制在 65-75 字符以内？
- 长段落是否有最大宽度限制？
- 不同断点下行长是否合理？

量化标准：
- 正文最大宽度：65-75 字符（约 550-650px）
- 使用 max-width 而非 width 限制

**2.6.4 字重层次**

检查项：
- 标题是否使用 600-700？
- 正文是否使用 400？
- 标签/辅助文本是否使用 500？
- 字重层次是否清晰？

量化标准：
- 标题字重：600-700
- 正文字重：400
- 标签字重：500
- 字重层次 ≥ 3 级

---

#### 2.7 间距审查

间距审查确保界面的空间组织一致和有节奏感。

**2.7.1 间距系统**

检查项：
- 是否使用 4/8dp 增量间距系统？
- 间距值是否来自预定义的间距 Token？
- 是否有随意的间距值？

量化标准：
- 所有间距值为 4 的倍数
- 使用间距 Token 而非魔法数字
- 间距值集：4, 8, 12, 16, 20, 24, 32, 40, 48, 64

**2.7.2 垂直节奏**

检查项：
- 是否有清晰的垂直节奏层级？
- 段落间距是否一致？
- 区块间距是否有规律？

量化标准：
- 段落间距统一（如 16px 或 24px）
- 区块间距 ≥ 2× 段落间距
- 垂直间距遵循倍数关系

**2.7.3 内边距一致性**

检查项：
- 组件内边距是否一致？
- 同类组件的内边距是否统一？
- 内边距比例是否合理？

量化标准：
- 同类组件内边距统一
- 按钮内边距：水平 ≥ 垂直
- 卡片内边距：16-32px

---

#### 2.8 布局审查

布局审查关注界面的整体构图和空间组织。

**2.8.1 构图**

检查项：
- 是否有明确的构图意图？
- 视觉重心是否在预期位置？
- 是否利用了网格系统？

量化标准：
- 使用网格系统（12列或8列）
- 视觉重心与内容优先级一致
- 首屏有明确的视觉焦点

**2.8.2 对齐**

检查项：
- 元素是否正确对齐？
- 是否有一致的对齐基线？
- 文本对齐是否合理？

量化标准：
- 所有元素对齐到网格

#### 2.15 Web Interface Guidelines 合规性审查

Web Interface Guidelines 合规性审查确保界面遵循现代 Web 平台的设计规范和最佳实践，与原生平台体验保持一致性。

**2.15.1 平台一致性**

检查项：
- 是否遵循目标平台的设计语言？（macOS/iOS 的 Human Interface Guidelines、Material Design、Fluent Design）
- 表单控件是否使用原生语义化元素（`<input>`、`<select>`、`<button>`）而非完全自定义？
- 滚动行为是否符合平台惯例？（惯性滚动、滚动条样式）
- 右键菜单、拖拽行为是否符合用户平台预期？

量化标准：
- 优先使用原生 HTML 语义化控件，仅在必要时自定义
- 表单元素保留原生焦点环和键盘行为
- 滚动体验与平台一致（macOS 平滑滚动、Windows 标准滚动）

**2.15.2 浏览器兼容性**

检查项：
- 是否支持主流浏览器的最近 2 个版本？（Chrome、Firefox、Safari、Edge）
- 是否使用了无前缀或带前缀的 CSS 属性？（flex、grid、clip-path）
- 是否使用了渐进增强（Progressive Enhancement）策略？
- 是否对旧浏览器有降级方案？

量化标准：
- 核心功能在所有目标浏览器中可用
- 使用 `@supports` 为高级特性提供条件支持
- 不使用仅被单个浏览器支持的实验性 API

**2.15.3 系统 UI 集成**

检查项：
- 是否尊重用户的系统偏好设置？（暗色模式、减少动效、高对比度）
- 是否使用了 `color-scheme` 让浏览器 UI 元素（滚动条、表单控件）适配主题？
- 是否使用了 `@media (prefers-contrast: high)` 支持高对比度模式？
- 是否正确处理了系统字体设置？

量化标准：
- 实现 `prefers-color-scheme` 适配（不仅手动切换，也响应系统设置）
- 实现 `prefers-reduced-motion` 适配
- 实现 `prefers-contrast` 适配
- 使用 `-apple-system`、`Segoe UI`、`Roboto` 等系统字体栈

**2.15.4 交互模式合规性**

检查项：
- 链接是否可识别为链接？（下划线、颜色区分、hover 状态）
- 按钮是否可识别为按钮？（明确的按钮样式，非纯文本）
- 表单提交是否遵循标准 HTTP 行为？
- 是否避免劫持系统快捷键？（Cmd/Ctrl+K、Cmd/Ctrl+F、Esc）
- 模态框是否可通过 Esc 关闭？
- 是否支持浏览器返回按钮导航？

量化标准：
- 链接必须有视觉区分（下划线或颜色 + hover）
- 按钮必须有明确的按钮样式（背景色、边框、圆角）
- 不劫持系统级快捷键
- 模态框/弹层支持 Esc 关闭和点击背景关闭
- SPA 应用正确处理浏览器历史（Back/Forward）

**2.15.5 表单最佳实践**

检查项：
- 是否使用了正确的 input type？（email、tel、number、date）
- 是否使用了 autocomplete 属性帮助浏览器自动填充？
- 是否使用了正确的 label 关联？（`<label for="">` 或隐式包裹）
- 是否阻止了浏览器的默认表单验证样式？（如需要，是否提供了替代方案）
- 文件上传是否支持拖拽？

量化标准：
- 所有输入使用语义化 type
- 表单字段使用 `autocomplete` 属性
- 每个输入都有关联 label
- 自定义验证样式覆盖或补充浏览器默认验证

**2.15.6 安全与隐私**

检查项：
- 密码输入是否使用了 `type="password"`？
- 敏感表单是否在 HTTPS 环境下提交？
- 是否使用了 `autocomplete="new-password"` 避免浏览器自动填充密码？
- 第三方嵌入（iframe、脚本）是否使用了适当的沙箱和 referrer 策略？

量化标准：
- 敏感输入使用正确的 type 和 autocomplete
- 外部资源使用 `rel="noopener noreferrer"`
- iframe 嵌入使用 `sandbox` 属性限制权限

### 3. 审查流程

审查遵循严格的流程，确保系统性和可重复性：

#### 步骤 1：读取目标文件/代码

- 使用 Read 工具读取目标文件
- 使用 Glob 工具发现相关文件
- 使用 Grep 工具搜索特定模式
- 识别制品类型（网站/应用/组件/文档）
- 确定审查范围（全量审查/增量审查）

#### 步骤 2：按维度逐项审查

- 按照 19 个维度的顺序进行审查
- 每个维度对照检查项逐项检查
- 记录发现的问题
- 对问题进行初步分级

#### 步骤 3：标记问题（高/中/低严重度）

**高严重度（❌）：**
- 影响核心功能可用性的问题
- 可访问性违规（WCAG AA 不通过）
- 严重的视觉/布局错误
- 性能严重问题（CLS > 0.25、LCP > 4s）

**中严重度（⚠️）：**
- 影响用户体验但不阻塞功能的问题
- 可访问性改进建议（WCAG AAA 目标）
- 视觉一致性问题
- 性能优化机会

**低严重度（💡）：**
- 锦上添花的改进
- 最佳实践建议
- 微小的视觉优化
- 代码质量改进

#### 步骤 4：提供具体改进建议

- 每个问题附带具体的改进建议
- 改进建议包含代码示例（如适用）
- 改进建议指明优先级
- 改进建议评估实施难度

#### 步骤 5：输出审查报告

- 按照标准格式输出审查报告
- 包含总体评分和维度评分
- 包含问题列表和改进优先级
- 报告可直接用于任务跟踪

### 5. 改进执行

审查后可直接执行改进，形成审查-改进-验证的闭环。

#### 5.1 执行原则

- **审查不改代码**：review 子技能的职责是发现问题，不直接修改代码
- **生成返修清单**：每个高/中严重度问题形成结构化返修任务
- **发回 design 子技能**：返修清单通过 pass-data.yaml 传递给 design 子技能
- **增量 mini-review**：design 修复后，仅对涉及维度重新审查

#### 5.2 审查→设计返修流程

1. **生成返修清单**：汇总所有高/中严重度问题
2. **写入 pass-data.yaml**：
   ```yaml
   rework-tasks:
     - id: REV-001
       dimension: "排版"
       severity: "high"
       issue: "ALL CAPS 缺少 letter-spacing"
       location: "index.html:45"
       suggestion: "添加 letter-spacing: 0.08em"
     - ...
   ```
3. **发回 design**：携带返修清单调回 design 子技能
4. **design 修复后 → mini-review**：仅对返修涉及的维度重新审查
5. **验证闭环**：确认所有返修任务完成

#### 5.3 返修清单格式

```yaml
# pass-data.yaml 中的返修段
rework-tasks:
  - id: string        # REV-{序号}

    issue: string      # 问题描述
    location: string   # 文件:行号
    suggestion: string # 具体修复建议
    status: pending|fixed|verified
```

#### 5.8 迭代改进

- 改进是一个迭代过程，可能需要多轮
- 每轮改进后重新审查，确认效果
- 当所有维度达到 ✅ 状态（≥8分）时，审查完成
- 最终输出改进总结报告
