# 阶段一：需求澄清详细指南

> 所属 Skill：`ai-dev-workflow`
> 目标：把模糊想法变成结构化的 PRD 文档

---

## 1. 本阶段目标

将用户的"我想做一个 XXX"转化为包含以下内容的 PRD 文档：

- 项目愿景和核心价值
- 目标用户画像
- 核心功能列表（按优先级）
- 非功能需求（性能、安全、可扩展性）
- 验收标准
- 外部依赖

---

## 2. AI 执行步骤

### 步骤 1：收集基本信息

向用户提问（每次 2-3 个问题，不要一次轰炸）：

```
必问问题：
1. 这个项目解决什么问题？目标用户是谁？
2. 最核心的 3 个功能是什么？（MVP 范围）
3. 有没有参考的竞品或类似项目？

选问问题（按需要）：
4. 预期的用户规模？（影响架构选型）
5. 有没有技术栈偏好或限制？
6. 有没有特殊的安全/合规要求？
7. 项目的时间约束？
```

### 步骤 2：生成 PRD 草案

基于用户回答，用以下模板生成 PRD.md：

```markdown
# {项目名称} — 产品需求文档 (PRD)

## 1. 项目概述
- **项目名称：** ...
- **一句话描述：** ...
- **目标用户：** ...
- **核心价值：** ...

## 2. 功能需求（按优先级）

### P0（MVP 必须）
- [ ] 功能A — 描述
- [ ] 功能B — 描述

### P1（重要但可延后）
- [ ] 功能C — 描述

### P2（锦上添花）
- [ ] 功能D — 描述

## 3. 非功能需求
- **性能：** ...
- **安全：** ...
- **可扩展性：** ...
- **可用性：** ...

## 4. 验收标准
- 用户能完成 X 操作的端到端流程
- 页面加载时间 < 2 秒
- ...

## 5. 外部依赖
- 第三方服务：...
- 基础设施：...
```

### 步骤 3：需求审查

检查以下项目并标注问题：

| 检查项 | 说明 |
|--------|------|
| 需求完整性 | 是否覆盖了功能+非功能+边界条件？ |
| 验收标准可测性 | 每个 User Story 是否有可量化的验收标准？ |
| 需求冲突检测 | 是否存在矛盾需求？（如"极致安全"和"极致速度"） |
| 粒度合理性 | 单需求预估工作量是否合理？ |
| 依赖风险 | 外部依赖是否已就绪或有替代方案？ |

### 步骤 4：用户确认

将 PRD 草案展示给用户，确认：
- 核心功能是否准确
- MVP 范围是否合理
- 验收标准是否可接受

**闸门条件：用户明确回复"确认"或"可以"后才进入下一阶段。**

---

## 4. AI 行为约束

- **不要一次性问超过 3 个问题**，用户会 overwhelmed
- **不要替用户做决策**（如"我觉得你应该用 React"），这属于阶段二
- **如果用户已经提供了详细需求**，直接生成 PRD 草案，不要重复提问
- **如果项目是已有项目改造**，跳转到审查模式而非从零开始

## 5. v3.1 增强：Spec Kit SDD 与 interview-me 协议

### 5.1 Spec-Driven Development（GitHub Spec Kit 范式）

v3.1 推荐将需求阶段拆分为 4 个 Slash 命令：

```
/spec    → 生成 spec.md（功能 + 非功能 + Out of Scope）
            关键：必须明确「不做什么」避免范围蔓延
/plan    → 生成 plan.md（架构 + 选型 + ADR 链接）
/tasks   → 拆分为可独立交付的子任务
/implement → 按 tasks 顺序执行（每任务独立 commit）
```

**Out of Scope 段落强制要求**：

```markdown
## 5. Out of Scope（v1.0 不做）

> 明确声明本版本不交付，避免 scope creep

- ❌ 第三方支付集成（v1.1 再说）
- ❌ 多语言 i18n（v1.0 仅支持中文）
- ❌ 移动端 App（v1.0 仅 Web）
- ❌ 高级数据分析（v1.0 仅基础报表）
```

### 5.2 interview-me 审讯协议（v3.0 引入，v3.1 强化）

**触发条件**（满足任一即触发）：
- 用户提"做一个系统/平台/管理后台"等模糊需求
- 用户给出"一般做法是…"等信号词
- 涉及支付、权限、安全、不可逆操作

**5 步协议**：

```
① CLAIM   → 复述用户的需求（确认理解）
② EXTRACT → 提取假设与未知
③ DOUBT   → 邀请用户质疑
④ ASK     → 一次只问一个关键问题
⑤ GUESS   → 附上 AI 的猜测 + 信心指数
```

**示例输出**（v3.1 标准格式）：

```markdown
**CLAIM：** 你想做一个"用户管理后台"，核心是 CRUD 用户。

**EXTRACT：**
- 假设：仅内部管理员使用
- 未知：用户量级、多租户需求、合规要求
- 风险：如果是多租户，权限模型完全不同

**GUESS：** 你大概率是 SaaS 系统的一部分，信心 70%。

**ASK：** 这个后台服务几个租户？
```

### 5.3 Context Engineering（2026 趋势）

不要追求"更长的 prompt"，而是追求"更结构化的上下文"：

| 上下文层级 | 存放位置 | 触发时机 |
|------------|----------|----------|
| 系统级 | AGENTS.md（项目通用） | 每个任务 |
| 项目级 | docs/agent-handbook.md | 详细查询 |
| 任务级 | 当次对话的 user message | 一次性 |
| 历史 | PR / Git log | retrieval |

### 5.4 vibe coding 边界

用户说"帮我写个完整 XX 系统"时，**禁止盲目全实现**：

```
❌ 错误做法：直接生成 50+ 文件
✅ 正确做法：
   1. 引导 Spec Kit 走 /spec → /plan → /tasks
   2. v1.0 只做 P0（MVP 3-5 个核心功能）
   3. 提供 2-3 个迭代路径供选择
```

## 6. v3.1 五大原则的体现

| 阶段 1 操作 | 触发的原则 |
|------------|------------|
| 先提问再写 PRD | Principle-5 (Plan Before Execute) |
| 拒绝"先做需求后面补" | Principle-2 (Test-Driven) 的"先思考后写" |
| 明确 Out of Scope | Principle-1 (Agent-First) 的"边界清晰" |
| 一次只问 1 个问题 | interview-me 协议 |
| PRD 中加"Assisted-by"声明 | Transparency 原则 |

## 7. v3.2 增强章节（基于用户反馈 2026-07-22 · 减法重构）

> **v3.2 关键变化：** v3.1 的"5 大原则都不可妥协"在实际项目中被证明**太严**，导致 AI 偷工减料、调研时过度轻量化。本节做减法——只保留**真正的红线**，其他全部改为**软性建议 + 场景适配**。

### 7.1 阶段 1 的规范应用强度（v3.2 重构）

| 规范 | v3.1 状态 | v3.2 状态 | 何时强化 | 何时弱化 |
|------|----------|----------|---------|---------|
| 先提问再写 PRD | 🔴 红线 | 🟡 软性建议 | 全新项目、复杂需求 | 明确任务、用户说"直接做" |
| 必须写完整 PRD | 🔴 红线 | 🟡 软性建议 | 多模块、跨团队 | 1-2 天可完成的小项目 |
| 一次只问 1 个问题 | 🔴 红线 | 🟡 软性建议 | interview-me 触发场景 | 用户明确"列出 5 个问题" |
| Out of Scope 必填 | 🔴 红线 | 🟡 软性建议 | 长期项目、多人协作 | 一次性脚本、演示原型 |
| Assisted-by 声明 | 🔴 红线 | 🟡 推荐（不阻塞） | 长期项目 | 个人项目、紧急修复 |

### 7.2 阶段 1 新增反模式（v3.2 减法哲学）

**AP-16 规范过度严苛：** 阶段 1 过度问询、要求详细 PRD、强迫写 Out of Scope → 用户放弃

**AP-17 轻量即正义：** AI 调研时以"不够轻量"为由删除有价值方案 → 用户选择空间被压缩

**AP-18 PRD 仪式化：** 为了写 PRD 而写 PRD，内容空洞无价值

### 7.3 v3.2 阶段 1 核心判断

```markdown
Q: 这个阶段 1 应该走多深？
A: 取决于 3 个问题：
  1. 项目预计周期？（< 1 周可简化 PRD）
  2. 团队规模？（单人可省略部分文档）
  3. 需求明确度？（明确可跳过审讯协议）
```

### 7.4 v3.2 阶段 1 决策树（替代 v3.1 的"必须走完流程"）

```
用户说"做一个 XXX"
  ├─ 明确功能 + 明确技术栈 + < 1 周 → 🟢 跳过详细 PRD，直接 /plan
  ├─ 明确功能 + 不明确技术栈 → 🟡 走 PRD + ADR，简化 Out of Scope
  ├─ 模糊需求（"我想做"） → 🔴 必须走 interview-me + PRD
  └─ 复杂需求（多模块、长期） → 🔴 完整流程
```

> **v3.2 哲学转变：** 规范是参考书，不是宪法。开发者判断 > 死规则。
