# neat vs 循环工程 工作流分工

> **来源**：LEARNINGS.md LRN-20260722-001 经验 7 + 项目收尾报告 5.6
> **目的**：明确两种工作流的适用场景，避免误用

---

## 0. 一句话核心

> **neat 是"整理"工具，循环工程是"开发"工具**。搞混会导致要么过度工程化（用 neat 做新功能），要么偷工减料（用循环工程做文档整理）。

---

## 1. 工作流对比

| 维度 | neat（整理） | 循环工程（开发） |
|------|-------------|-----------------|
| **目标** | 整理、盘点、归档 | 实现功能、修复 bug、调整 UI |
| **产出** | 文档/清单/报告 | 代码 + 测试 + 文档 |
| **流程步骤** | 6 步（见 2.1）| 8 步（见 2.2）|
| **角色** | 单 agent 即可 | 多 subagent（implementer + spec-reviewer + code-quality-reviewer）|
| **测试要求** | 不需要 | 必跑 L1 + L2（绿门全禁）|
| **commit 频率** | 一次性或按章节 | 每任务独立 commit |
| **失败处理** | 自检清单 | 修复 → 重新双审 |

---

## 2. neat 工作流（整理）

### 2.1 标准 6 步流程

```
尺寸体检 → 盘点现状 → 识别变更 → 实际修改 → 自检清单 → 变更摘要
   1          2          3          4          5          6
```

| 步骤 | 内容 | 工具 |
|------|------|------|
| **1. 尺寸体检** | 检查文件行数、文档长度、目录深度 | `wc -l`, `tree` |
| **2. 盘点现状** | 列出所有相关文件 + 状态 | `Glob`, `Read` |
| **3. 识别变更** | 标记需保留 / 需修改 / 需删除 | 自审 |
| **4. 实际修改** | 移动/重命名/删除/重构 | `Edit`, `Write`, `DeleteFile` |
| **5. 自检清单** | 跑 lint/typecheck 验证没破坏构建 | `npm run lint && npm run typecheck` |
| **6. 变更摘要** | 报告做了什么 + 为什么 | `.learnings/neat-report-YYYYMMDD.md` |

### 2.2 neat 适用场景

| ✅ 适用 | ❌ 不适用 |
|--------|----------|
| 文档整理（README/AGENTS.md/CLAUDE.md 重构）| 新功能开发（应该用循环工程 + spec 三件套）|
| 现状盘点（代码审计/依赖梳理/死代码扫描）| UI 调整（应该用 dogfood 端到端验证）|
| 计划制定（Phase 路线图/复兴计划/改进项）| Bug 修复（应该用 systematic-debugging）|
| 目录索引（PROJECT-INDEX.md）| 实际代码变更（应该用循环工程）|
| 经验归档（LEARNINGS.md 整理）| — |
| 目录重构（projects/ 重组）| — |

### 2.3 neat 反模式

```yaml
# ❌ 错误：用 neat 做新功能
"我要做用户登录功能，先整理下项目结构"
→ 实际应该用循环工程（spec + implementer + spec-reviewer + code-quality-reviewer）

# ❌ 错误：用循环工程做文档整理
"我要重构 AGENTS.md，启动循环工程"
→ 实际应该用 neat（不需要 spec 三件套，不需要双审）

# ❌ 错误：把 neat 当成"快速模式"的循环工程
"我没时间跑循环工程，用 neat 模式实现这个功能吧"
→ 实际就是偷工减料，不是 neat 的适用场景
```

## 3. 循环工程工作流（开发）

### 3.1 标准 8 步流程

```
spec → implementer → spec-reviewer → code-quality-reviewer → fix → dogfood → commit → 归档
  1         2              3                  4                5        6        7       8
```

| 步骤 | 角色 | 产出 |
|------|------|------|
| **1. spec** | 主 agent | spec.md（what & why）+ tasks.md（分解）+ checklist.md |
| **2. implementer** | subagent | 代码 + 测试 |
| **3. spec-reviewer** | subagent | 是否符合 spec / 有无 over-engineer |
| **4. code-quality-reviewer** | subagent | 安全/性能/正确性/可维护性/测试/可访问性/文档 |
| **5. fix** | implementer | 修复审查发现的问题 |
| **6. dogfood** | 真实环境 | 端到端验证（截图+复现步骤）|
| **7. commit** | 主 agent | 独立 commit（每任务一个）|
| **8. 归档** | 主 agent | LEARNINGS.md + PROGRESS.md + AGENTS.md 更新 |

### 3.2 循环工程适用场景

| ✅ 适用 | ❌ 不适用 |
|--------|----------|
| 新功能开发（spec → 实现）| 文档整理（应该用 neat）|
| Bug 修复（systematic-debugging + 循环工程）| 现状盘点（应该用 neat）|
| UI 调整（实现 → dogfood）| 计划制定（应该用 neat）|
| 重构（spec → 实现 → 双审）| 简单 typo 修复（直接改）|
| 性能优化（profiling → 实现 → 基准测试）| — |

### 3.3 循环工程反模式

```yaml
# ❌ 错误：跳过 spec
"这个功能很简单，不用写 spec，直接实现"
→ 实际应该用循环工程的精简流程（最小 spec + 实施 + 双审）

# ❌ 错误：跳过 dogfood
"代码改完跑过三绿门禁了，可以发布"
→ 实际违反 L0-03 红线（三绿门禁必要非充分），必须 L3 端到端

# ❌ 错误：双审走过场
"spec-reviewer 说没问题，code-quality-reviewer 说没问题，直接合并"
→ 实际可能错过关键问题，必须看具体审查意见

# ❌ 错误：把 neat 当成循环工程的"快速模式"
"我没时间跑完整 8 步，用 neat 模式实现吧"
→ 实际是偷工减料，不是 neat 的适用场景
```

## 4. 决策树

```
Q: 你要做什么？
A:
  ├─ 整理/盘点/归档/计划 → neat（6 步）
  │
  ├─ 实现/修复/调整/重构 → 循环工程（8 步）
  │   ├─ 简单改 1-2 文件 → 循环工程精简版（最小 spec + 实施 + dogfood）
  │   └─ 复杂多文件改动 → 循环工程完整版（8 步）
  │
  └─ 修一个 typo/改一行配置 → 直接改（不需要任何工作流）
```

## 5. 真实案例：知行读书 Phase 6

### 5.1 错用 neat 做 UI 调整（反面案例）

**错的事**：
- Phase 6 实施了 11 项 UI 调整
- 没用循环工程（spec → implementer → dogfood）
- 只跑三绿门禁就宣布完成
- 用户实测发现 5 个暗色模式 bug

**正确做法应该是**：
- 用循环工程：spec.md（UI 调整规范）+ implementer（改代码）+ spec-reviewer（检查符合度）+ dogfood（截图验证暗色模式）

### 5.2 正确用 neat 做经验归档（正面案例）

**对的事**：
- Phase 6 完成后用 neat 工作流整理项目目录
- 9 个任务（目录索引 + 约定重构 + Phase 7 计划）一天内完成
- 用户验收通过

**为什么对**：
- neat 适用场景（文档整理/现状盘点/计划制定）
- 不需要 spec 三件套（不是新功能）
- 不需要双审（不是代码变更）
- 输出是文档/清单/报告

## 6. 实操检查清单

### 6.1 启动任务前必问

```
□ 这是"整理"还是"开发"？
  ├─ 整理：目标 = 文档/清单/报告 → neat
  └─ 开发：目标 = 代码/测试/功能 → 循环工程

□ 涉及的产出是什么？
  ├─ 文档/计划/索引 → neat
  └─ 代码/测试/UI → 循环工程

□ 需要测试吗？
  ├─ 不需要（整理类）→ neat
  └─ 需要（开发类）→ 循环工程

□ 需要 spec 三件套吗？
  ├─ 不需要（整理类）→ neat
  └─ 需要（开发类）→ 循环工程
```

### 6.2 工作流选择错误的后果

| 错用 | 后果 | 真实案例 |
|------|------|---------|
| 用 neat 做新功能 | 跳过 spec → 实现不符合预期 | （假设案例）|
| 用循环工程做文档整理 | 过度工程化，浪费资源 | （假设案例）|
| 把 neat 当快速模式 | 偷工减料，跳过双审 | Phase 6 11 项 UI 调整（错用 neat）|
| 把循环工程当完整流程 | 小修改也跑 8 步，效率低 | （假设案例）|

---

## 7. 核心结论

1. **neat 整理，循环工程开发**——不要搞混
2. **neat 6 步不需要测试**——因为是整理不是开发
3. **循环工程 8 步必跑 L3 端到端**——绿门全禁是 L0-03 红线
4. **工作流选择错了会踩坑**——Phase 6 11 项 UI 调整错用 neat 是反面案例
5. **决策树先问"整理还是开发"**——目标决定工作流

> **最终警告**：工作流是工具不是枷锁。明确边界，按场景选择，不要把 neat 当快速模式。
