# project-prep · 个人项目开发前置

一句话：**先把「做什么、怎么搭、怎么写、怎么跑、做到哪、AI 怎么配合」写清楚，再写代码。**

本 skill 只产出文档，不写业务代码。文档不是形式，是开工前的约束：每份文档都要能回答一个具体问题，并带可核验的验收判据。

## 一、三条铁律

1. **文档门未过，不写业务代码。** 允许写不超过 1 天的探索性 spike，但必须在 `05-项目进度控制.md` 登记「为什么写、验证什么、结论」。
2. **不写空值。** 禁止「待定」「TBD」「稍后补」「正常」「暂无」；判不了就写「无法判定 + 缺哪份依据 + 谁补 + 何时」。空值等于把问题留给未来的自己。
3. **开源方案必须三查。** 查许可证、查维护状态、查已知安全问题；README 的宣传语不算证据，必须看仓库本体（LICENSE、最近提交、issue、CVE）。

## 二、技术经理人三视角

| 视角 | 对应动作 | 产物 |
|---|---|---|
| 需求对接（产品经理） | 问清谁用、为什么现在做、现状怎么解决、成功长什么样 | `01-项目开发文档.md` |
| 成果端调研（开源） | 找可复用的开源件，判断许可证、维护、安全、抄哪一部分 | `02-架构与技术栈.md` 的能力来源表 |
| 落地中试（demo 验证） | 真数据跑一条主路径，记录「哪里崩了」，再谈本地到云端 | `04-本地初始化与运行.md`、`05-项目进度控制.md` |

## 三、三步流程与文档门

```
第 1 步 立项澄清   → 01 项目开发文档
第 2 步 设计与约束 → 02 架构与技术栈 + 03 开发规范
第 3 步 落地准备   → 04 本地初始化与运行 + 05 进度控制 + 06 AI 协作规范 + README 索引
                  ↓
              文档门检查（7 份齐全、无空值、验收可观察）
                  ↓
              允许开始编码（交给 ai-dev-workflow 或直接开发）
```

每一步结束时向用户回显「已确认 / 仍是假设 / 待补」，确认后再进入下一步。用户明确说「跳过」时，在 05 中记录跳过项与代价。

## 四、7 份文档各自回答什么

| 文档 | 回答的问题 | 必须写清 | 常见坑 |
|---|---|---|---|
| `01-项目开发文档.md` | 做什么？为什么做？功能是什么？怎样验收？ | 一句话目标、非目标、P0/P1/P2 功能、每条功能的验收判据、约束 | 只写「更好用」不写判据；没有非目标导致范围蔓延 |
| `02-架构与技术栈.md` | 用什么技术？怎么分层？模块怎么组织？数据怎么流动？ | 技术栈表（选它的理由 + 不选备选的理由）、能力来源表、分层、模块边界、数据流、部署目标 | 先选框架再找理由；开源件只看 README；不写数据流导致模块互相穿透 |
| `03-开发规范.md` | 代码怎么写？组件怎么组织？哪些行为被约束？ | 目录结构、命名、格式化/lint、错误处理、日志、配置与密钥、Git 规范、质量门、AI 编码附加规则 | 规范写成口号没有检查动作；密钥进仓库 |
| `04-本地初始化与运行.md` | 环境怎么配？依赖怎么装？怎么启动、构建、测试？ | 前置版本、一次性初始化、环境变量表、开发/构建/测试命令、10 分钟冒烟、故障排查、本地→云端差异 | 只写「按需配置」；命令没真跑过；忽略路径大小写、端口、时区差异 |
| `05-项目进度控制.md` | 做到哪了？下一步做什么？怎么算验收？ | 当前状态、里程碑表、当前迭代、下一步三件事、阻塞、决策记录、验收记录 | 状态与代码不一致；验收没有证据落点；决策不记原因 |
| `06-AI协作规范.md` | 人和 AI 怎么分工？方案怎么确认？结果怎么审查？ | 分工原则、方案确认门、上下文交接格式、审查清单、禁止行为、模型/提示词版本记录 | 让 AI 自证成功；AI 擅自扩大改动范围；会话结束不留交接 |
| `README.md` | 从哪开始读？ | 一句话、文档索引、快速开始、当前阶段、目录结构 | 索引指向不存在的文件；README 与文档说两套话 |

每份文档的逐项检查表见 `references/doc-checklists.md`。

## 五、怎么问

- 一次最多问 5 个问题，按「目标 → 用户 → 约束 → 验收」排序。
- 能从上文推断的不问；不确定的才问。
- 每个问题自带一个可否决的默认答案：「这项你不答，我按 X 推进，代价是 Y」。
- 需求描述里出现「更好」「智能」「高效」这类词，必须追问成可观察的判据（谁在什么场景下，做什么动作，达到什么数字或状态）。
- 用户说不清时，先给一个最小可验证版本，再让用户否决，不要停下来等。

## 六、开局动作

```bash
# 在目标项目根目录执行（把 <skill> 换成本 skill 实际路径）
python <skill>/scripts/init_project_docs.py --target <项目根目录> --name "<项目名>"

# 如希望生成的文档默认不进 git
python <skill>/scripts/init_project_docs.py --target <项目根目录> --name "<项目名>" --ignore-docs
```

脚本只搭骨架（拷贝 7 个模板并替换项目名/日期），不填内容。已存在的文件默认不覆盖，加 `--force` 才覆盖。

生成后按第 1 → 2 → 3 步逐份填写；填完一份跑 `references/doc-checklists.md` 对应小节的检查表。

## 七、文档门（编码前必过）

全部满足才允许开始写业务代码：

- [ ] 7 份文档都存在且非空
- [ ] 01 的每条 P0/P1 功能都有可观察的验收判据
- [ ] 01 明确写了非目标
- [ ] 02 的每个技术选择都有「选它的理由」和「不选备选的理由」
- [ ] 02 的开源候选都过了「许可证 / 维护 / 安全」三查
- [ ] 02 写出了数据流和部署目标
- [ ] 03 的每条规范都有检查动作（lint 规则、脚本或人工检查项）
- [ ] 03 明确了密钥与配置的管理方式
- [ ] 04 的命令都在本机真跑过一次，并写明预期输出
- [ ] 04 列出了本地与云端的环境差异及处置
- [ ] 05 有里程碑、当前状态、下一步三件事
- [ ] 06 有方案确认门、审查清单、禁止行为
- [ ] README 的每条索引都能打开
- [ ] 全文无「待定 / TBD / 稍后补 / 正常 / 暂无」

## 八、维护规则

- `05` 是活文档：每完成一个任务就更新状态；每次会话结束更新「下一步三件事」。
- `01`、`02` 变更要留痕：在文档末尾的「变更记录」写日期、改了什么、为什么。
- 任何与文档不一致的实现，要么改代码，要么改文档，不允许长期两套话。
- `README` 是唯一入口：新增文档必须登记进索引，删除文档必须从索引移除。

## 九、与其他 skill 的分工

| 能力 | 用谁 | 本 skill 做什么 |
|---|---|---|
| 想法 → 产品方案、平台选型、可行性论证 | `idea-to-dev` | 消费其结论，写成可开工的 01/02 |
| 开源项目检索与深度调研 | `oss-finder` / `deep-research-ultra` | 消费检索结果，按「三查」写进 02 的能力来源表 |
| 编码规范、脚手架、质量门、TDD | `ai-dev-workflow` | 在 03 中引用其场景化规范，并补 AI 协作附加规则 |
| 交付判断、验收、效果度量 | `fde`（如已安装） | 个人项目只取「基线 / 样本量 / 证据等级」的口径，不照搬七段状态机 |

## 十、禁止清单

- 禁止用文档数量冒充准备充分：7 份文档写完但全是套话，等于没写。
- 禁止把「待定」当结论，禁止用「以后优化」代替降级方案。
- 禁止在没有跑过命令的情况下编写 04 的启动步骤。
- 禁止把开源项目的宣传语当能力证据；必须写清「抄哪一部分、不抄什么」。
- 禁止在 06 中允许 AI 自行确认方案、自行判定验收通过。
- 禁止把密钥、Token、连接串写进任何文档或示例配置。
- 禁止为个人项目套用企业级流程：文档规模与项目规模匹配，简单项目允许合并章节，但 7 份文件与文档门不可省。
