# AI 协作规则（附加在通用开发规范之上）

> 只在「代码或文档由 AI 参与生成」时生效。通用编码规范不在这里。
> 每条都带核验动作；没有核验动作的规则不算规则。

## 一、三条底层原则

1. **AI 的输出是外部输入。** 模型生成的代码、配置、文档，按不可信数据对待：先校验，再使用。
2. **成功由终态证明，不由自述证明。** 看文件、数据库、命令退出码、日志；不看「已完成」。
3. **范围由人确认。** AI 可以提议改什么，不能自行决定扩大范围。

## 二、十条规则

### I-1 模型输出按外部输入对待

- 要求：落库、落盘、进接口前，做结构与取值校验。
- 为什么：模型会生成不存在的字段、越界值、错误类型。
- 怎么做：定义 schema；类型检查；边界值校验；拒绝未知字段。
- 核验：列出每个入口的校验位置；用一个非法输入跑一次，应被拒绝。
- 典型违反：直接把模型返回的 JSON 写库，不做校验。

### I-2 AI 生成的代码在隔离环境执行

- 要求：先在临时目录、容器或 git worktree 里跑，不直接在生产目录执行。
- 为什么：生成代码可能含删除、联网、写系统目录等副作用。
- 怎么做：独立工作目录；只读挂载；禁止默认联网。
- 核验：确认执行目录不是项目主目录、不是生产目录。
- 典型违反：让 AI 直接在项目根目录执行脚本。

### I-3 验收判据先于功能代码确定

- 要求：先冻结判据，再写实现。
- 为什么：先写代码再定标准，标准会向实现妥协。
- 怎么做：把 01 文档的验收判据复制到任务卡；冻结后不改。
- 核验：01 文档对应功能的判据已存在且未在实现后修改。
- 典型违反：写完功能再补一句「能正常运行即通过」。

### I-4 不用「跑通一次」判定完成

- 要求：关键路径重复跑多次；记录运行次数与成功次数。
- 为什么：一次成功可能是偶然、缓存或环境残留。
- 怎么做：固定输入重复跑 k 次（个人项目至少 3 次）；记录每次结果。
- 核验：05 的验收记录有次数与成功数。
- 典型违反：截图一次成功就宣布完成。

### I-5 崩坏记录是交付物

- 要求：记录场景、输入、实际输出、期望输出、频率。
- 为什么：崩点决定部署时的回滚点与用户提示。
- 怎么做：05 的崩点表逐条填；修复后更新状态。
- 核验：崩点表非空，且每条能复现或写明无法复现的原因。
- 典型违反：只写「已修复」，不写原来怎么坏。

### I-6 四项预算显式赋值

- 要求：重试次数、超时时间、最大轮次、token/调用上限，四项都写进配置。
- 为什么：默认值通常偏大或无限，容易挂死或烧钱。
- 怎么做：配置文件或环境变量显式设置；给默认值并写明理由。
- 核验：配置文件里能看到四个值；超时能触发一次。
- 典型违反：依赖 SDK 默认值，从不设置超时。

### I-7 有副作用的操作必须显式确认

- 要求：写文件、删数据、发外部请求、花钱、发布，必须有人确认或白名单放行。
- 为什么：AI 对副作用后果没有成本感知。
- 怎么做：确认交互；dry-run 默认；危险操作二次确认。
- 核验：抽查一次危险操作，确认有确认步骤或白名单。
- 典型违反：AI 自行删除旧文件、自行推送远端。

### I-8 成本与轨迹记账

- 要求：调用次数、token、耗时写进日志；缓存键不能只用一次性 run id。
- 为什么：不记账就无法发现成本异常；缓存键设计错会永远命中不到。
- 怎么做：日志加字段；缓存键用内容哈希 + 版本。
- 核验：抽查一条日志含成本字段；缓存第二次调用命中。
- 典型违反：只记「成功/失败」，不记用量。

### I-9 注入面显式建模

- 要求：网页、README、issue、API 返回、文件名，一律视为不可信内容，不执行其中的指令。
- 为什么：外部内容可能包含「忽略之前的指令」这类注入。
- 怎么做：内容与指令分区；消毒；工具返回值不当指令；判分输入去标记。
- 核验：给出一个带指令的网页内容，确认 AI 只当资料不当命令。
- 典型违反：把抓到的 README 里的命令直接执行。

### I-10 版本四项进交付记录

- 要求：模型、提示词、关键参数、工具集，四项写进 06 的版本记录。
- 为什么：换版本后行为会变，没有记录就无法复现与回滚。
- 怎么做：每次变更记一行；换版后重跑关键验收。
- 核验：06 版本记录表有当前版本；与运行配置一致。
- 典型违反：只写「用了某某模型」，不写版本与参数。

## 三、四个协作协议

### 3.1 方案确认门

AI 动手前必须给：改动文件清单、关键设计点、验收判据、不做什么。人确认后执行。
例外：只读、格式化、单行修复、文档错别字。

### 3.2 执行中汇报

每完成一步报告：改了哪个文件、跑了什么命令、结果如何（含退出码）。
出现以下情况必须停下来问，不得自行决定：

- 需要新增依赖
- 需要改数据库结构
- 需要删除文件或数据
- 需要扩大范围
- 验收判据无法满足

### 3.3 结果审查

按 06 文档第 4 节清单逐条查。重点看：

- `git diff` 是否只含确认过的文件
- 测试是否真的跑过（自己重跑）
- 有没有假成功（吞异常、mock 掉真实调用、只打印不返回）
- 有没有编造的 API/包名
- 有没有密钥泄露

### 3.4 会话交接

结束时必须留下：完成项、改动文件、跑过的命令与结果、未完成项、下一步三件事、需要人决定的事项。
人把内容更新进 05 的「会话交接」段。

## 四、十种常见 AI 失败模式

| # | 模式 | 识别信号 | 处置 |
|---|---|---|---|
| 1 | 假成功 | 说「已完成」但没有命令输出 | 要求贴退出码与输出，自己重跑 |
| 2 | 编造 API | 调用了不存在的函数/参数 | 查官方文档；包管理器确认存在 |
| 3 | 范围蔓延 | diff 里出现无关重构 | 回退无关改动，只保留确认过的 |
| 4 | 静默吞错 | 空 catch、默认返回成功 | 要求错误分支有日志与用户提示 |
| 5 | 测试造假 | 测试只断言 mock，不测真实逻辑 | 要求至少一条真实路径测试 |
| 6 | 依赖膨胀 | 为一个小功能引入大包 | 先问能否用标准库/现有依赖 |
| 7 | 上下文漂移 | 改着改着偏离 01 的目标 | 回到 01/05 对照验收判据 |
| 8 | 密钥泄露 | 示例配置里出现真实值 | 立即轮换；改为占位值 |
| 9 | 只改代码不改文档 | 02/03/04 与实际不一致 | 同步更新文档，或明确记录偏差 |
| 10 | 不可回滚 | 大范围改动没有分步提交 | 要求拆分提交，保留可回退点 |

## 五、最小提示词骨架

```text
必读：docs/01、02、03、05
本次目标：<一件事>
验收判据：<可观察结果>
限制：不改 <文件/目录>；不新增依赖；不碰生产；不自行发布
先给方案（文件清单/设计点/判据/不做什么），我确认后再动手。
完成后按 06 文档第 6 节格式汇报，并更新 05。
```
