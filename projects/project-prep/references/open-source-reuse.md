# 开源成果端调研（能力来源）

> 用途：02 文档第 3 节的展开说明。
> 核心：**先找可复用的成果，再决定自己写多少。** 调研开源项目不是看 README，是查仓库本体。
> 原则：README 是宣传材料，许可证、提交记录、issue、CVE 才是证据。

## 一、什么时候做

- 新项目选型前：确认有没有成熟轮子。
- 某个模块要自己写之前：确认是否已有可复用实现。
- 引入依赖前：确认许可证、维护状态、安全风险。

个人项目时间有限，优先级：**用现成的 > 抄一小部分 > 只抄思路 > 自己写**。

## 二、五步法

### 第 1 步：定义能力面

把需求拆成能力，不要按「我想用什么库」去找。

| 能力面 | 本项目需要什么 | 可接受的开源形态 |
|---|---|---|
| 例：文件解析 | 解析 PDF 文本 | 库 / CLI / 服务 |
| 例：定时任务 | 每天跑一次 | 库 / 平台能力 |
| 例：鉴权 | 单用户登录 | 库 / 框架内置 |

### 第 2 步：检索候选

优先用现成检索能力，不手工翻：

- 本工作区有 `oss-finder` / `deep-research-ultra` 时，先用它们检索。
- 没有时，用包管理器与代码托管平台的搜索：

```bash
# Python
pip index versions <包名>
# Node
npm view <包名> repository license time.modified
# GitHub（需 gh CLI）
gh repo view <owner>/<repo> --json name,licenseInfo,pushedAt,stargazersCount,openIssuesCount,archived
gh api repos/<owner>/<repo>/commits?per_page=1
```

### 第 3 步：三查

#### 3.1 查许可证

| 许可证 | 个人项目可用性 | 注意 |
|---|---|---|
| MIT / Apache-2.0 / BSD | 可用 | 保留版权声明 |
| MPL-2.0 | 可用 | 修改的文件需开源 |
| LGPL | 可用（动态链接） | 静态链接/修改需评估 |
| GPL / AGPL | 谨慎 | 传染性强；AGPL 对网络服务也生效 |
| 无 LICENSE 文件 | 视为不可用 | 默认保留所有权利 |
| 自定义/商用限制 | 逐条读 | 可能禁止商用或限制用户数 |

核验动作：打开仓库根目录的 `LICENSE` 文件，记录许可证全名与取证日期。不要只看 GitHub 侧边栏徽章。

#### 3.2 查维护状态

| 信号 | 判断 |
|---|---|
| 最近 12 个月有提交 | 活跃 |
| 6–12 个月无提交 | 低维护，可用但准备接手 |
| 超过 12 个月无提交 / archived | 停更，只抄思路，不直接依赖 |
| issue 长期无人回复 | 维护风险高 |
| 只有一个人维护且无发版记录 | 中等风险 |

核验动作：记录最近提交日期、最近发版日期、open issue 数。用 `gh api` 或仓库页面取证。

#### 3.3 查安全

- 查仓库的 Security 公告 / Releases 里的 CVE 修复记录。
- 查依赖链：`pip-audit`、`npm audit`、`osv-scanner`（有则用）。
- 无法确认时写「未取证」，禁止写「没有漏洞」。

核验动作：记录查询工具、查询日期、结果。CVE 结论必须带查询口径。

### 第 4 步：定复用边界

每个候选必须回答：

- **抄哪一部分**：具体到目录/文件/函数，不写「参考整体设计」。
- **不抄什么**：认证、计费、遥测、庞大依赖、与本项目无关的模块。
- **怎么接**：直接依赖 / fork 后裁剪 / 复制单文件 / 只抄思路。
- **出问题怎么办**：停更后谁维护；能不能替换；替换成本。

### 第 5 步：写进 02 的能力来源表

| 能力面 | 候选 | 许可证 | 最近提交 | 维护状态 | 安全问题 | 抄哪部分 | 不抄什么 | 结论 |
|---|---|---|---|---|---|---|---|---|
| | | | | | | | | 用 / fork / 抄思路 / 自研 |

结论必须四选一，不写「可以考虑」。

## 三、决策规则

```
有活跃维护 + 许可证兼容 + 无高危漏洞
  ├─ 功能覆盖 80% 以上 → 直接用
  ├─ 只覆盖一部分 → fork 裁剪，或复制需要的单文件
  └─ 依赖过重 → 只抄思路，自己写最小实现

停更 / 许可证不兼容 / 有未修复高危漏洞
  ├─ 只抄设计思路（不复制代码）
  └─ 自己写，或换候选
```

## 四、常见错误

| 错误 | 为什么错 | 正确做法 |
|---|---|---|
| 只看 star 数 | star 多不等于适合你 | 看许可证、维护、依赖、代码量 |
| 只看 README 功能列表 | 宣传不等于实现 | 看源码与测试 |
| 直接 clone 整个仓库 | 带入大量无关代码与依赖 | 只取需要的目录/文件 |
| 忽略许可证 | 商用/分发时出问题 | 查 LICENSE 本体，记录全名 |
| 把停更项目当长期依赖 | 出问题无人修 | 只抄思路或准备接手 |
| 写「没有 CVE」 | 没查不等于没有 | 写查询工具、日期、范围 |
| 不写「不抄什么」 | 把认证/计费/遥测一起搬进来 | 明确排除清单 |

## 五、输出要求

- 每个候选一行，结论四选一。
- 每个数字带取证日期。
- 每个许可证带全名与链接。
- 每处「未取证」写清缺什么、谁补、何时补。
- 选定的方案要写进 02 的 ADR：为什么选它、放弃了什么、何时重评。

## 六、个人项目最小版

时间紧时至少做三件事：

1. 打开候选仓库的 LICENSE，确认可用。
2. 看最近一次提交日期，判断是否停更。
3. 看依赖数量与包体积，判断是否过重。

三项都过再引入；任一不过，只抄思路。
