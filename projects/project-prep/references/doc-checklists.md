# 文档检查表（文档门判据）

> 用途：每份文档填完后逐条勾对；7 份全部通过才允许写业务代码。
> 原则：**没有证据的结论视为未填写；空值视为未通过。**

## 0. 通用规则

### 0.1 空值黑名单

以下词出现在待填位置，一律视为未完成：

`待定`、`TBD`、`待补充`、`稍后补`、`正常`、`暂无`、`见附件`、`以后再优化`、`按需配置`、`视情况而定`。

替代写法：`无法判定 + 缺哪份依据 + 谁补 + 何时补`。

### 0.2 判据写法

每条结论至少满足一项：

- 有来源（文件路径、命令输出、链接 + 取证日期）。
- 有数字或可观察状态（次数、耗时、文件、返回码）。
- 明确标注为「假设」，并写验证方式与验证时点。

### 0.3 规模控制

个人项目文档不追求篇幅：01 ≤ 2 页、02 ≤ 3 页、03 ≤ 3 页、04 ≤ 3 页、05 持续增长、06 ≤ 2 页。超出时优先删套话，不删判据。

## 1. 01 项目开发文档

- [ ] 一句话目标写清了「为谁、解决什么、达到什么」，不是功能罗列
- [ ] 背景问题有事实或数字，不是「不方便 / 效率低」
- [ ] 主要用户、使用场景、使用频率写清
- [ ] 非目标至少 2 条，且是本期明确不做
- [ ] 每条 P0/P1 功能都有输入、处理、输出、验收判据
- [ ] 验收判据可观察（能通过命令、操作或数字判定）
- [ ] Definition of Done 覆盖功能、稳定性、数据、文档、可运行
- [ ] 约束写了时间、预算、平台、数据、合规
- [ ] 假设全部显式列出，并写验证方式
- [ ] 没有空值黑名单词

**驳回条件**：功能没有验收判据；没有非目标；把「界面美观」当判据。

---

## 2. 02 架构与技术栈

- [ ] 技术栈表每一行都有「选它的理由」和「不选备选的理由」
- [ ] 没有出现「先选框架再补理由」的痕迹（理由能追到 01 的约束）
- [ ] 能力来源表每个候选都写了许可证、最近提交、维护状态、安全问题
- [ ] 每个开源候选都写了「抄哪一部分、不抄什么」
- [ ] 停更 / 无许可证 / 有高危漏洞的项目有明确结论（不用或只抄思路）
- [ ] 分层表写清每层职责、允许依赖、禁止事项
- [ ] 模块表写清输入、输出、依赖、负责人
- [ ] 数据流有一条完整主路径，并写了失败时怎么办
- [ ] 外部依赖写了不可用时的降级方案
- [ ] 部署目标与本地差异有初步对照
- [ ] 关键决策有 ADR 记录（决策、原因、放弃了什么、何时重评）

**驳回条件**：技术选择没有备选对比；开源件只看 README；没有数据流。

## 3. 03 开发规范

- [ ] 目录结构与本项目实际一致
- [ ] 命名、格式化、lint、类型检查都有工具与命令
- [ ] 每条规范都有检查动作（工具、命令或人工检查项）
- [ ] 错误处理写了可恢复/不可恢复的区分
- [ ] 日志写了必记字段与禁记字段
- [ ] 配置与密钥写了管理方式，明确 `.env` 不进仓库
- [ ] 数据迁移写了回滚方式
- [ ] Git 规范写了分支、提交信息、禁止项
- [ ] 质量门写了四项（格式化/lint/类型/测试）的命令与通过标准
- [ ] AI 编码附加规则 I-1 ~ I-10 全部有核验动作
- [ ] 禁止清单存在

**驳回条件**：规范只有口号没有检查动作；允许密钥进仓库；质量门没有命令。

## 4. 04 本地初始化与运行

- [ ] 前置工具、版本、检查命令、预期输出齐全
- [ ] 初始化步骤按顺序可执行，含 Windows 与 macOS/Linux 差异
- [ ] 环境变量表写了必填、示例、说明、是否敏感
- [ ] 启动、构建、测试命令都在本机真跑过，并写了预期输出
- [ ] 有 10 分钟冒烟测试表
- [ ] 常见故障排查覆盖端口、依赖、路径、编码、数据库
- [ ] 本地→云端 20 项差异逐项有处置
- [ ] 数据备份与恢复步骤写清
- [ ] 部署前检查清单存在

**驳回条件**：命令没跑过；写「按需配置」；没有本地→云端差异表。

## 5. 05 项目进度控制

- [ ] 当前状态一句话能说清「能做什么、不能做什么」
- [ ] 里程碑有交付物、验收判据、计划/实际完成
- [ ] 当前迭代任务有状态与证据落点
- [ ] 下一步三件事具体到可执行
- [ ] 阻塞项写了卡点、需要谁、已等多久、临时绕法
- [ ] 决策记录写了原因与影响
- [ ] 验收记录有判据、实际结果、证据位置、结论
- [ ] 崩点记录有场景、输入、实际/期望输出、频率
- [ ] 跳过项写了代价与补做时点
- [ ] 会话交接段能在新会话直接恢复工作

**驳回条件**：状态与代码不一致；验收没有证据；只记成功不记崩点。

- [ ] 分工表写清 AI 可做与必须由人做的事项

- [ ] 审查清单至少覆盖改动范围、依赖、密钥、假 API、假成功、测试真实性

- [ ] 至少 4 个可复用提示词模板

**驳回条件**：允许 AI 自行判定验收；没有审查清单；没有交接格式。
