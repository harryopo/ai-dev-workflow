# Token 优化最佳实践

## 核心理念

> **控制什么进入上下文，控制会话如何累积，控制工具向上下文倾倒什么。**

## 一、设置层优化（一次性）

### 1.1 .claudeignore 配置

**目标：** 阻止 Claude 读取高成本文件

**原则：**
- Claude 完成工作不需要看到的内容，不应该对它可见
- 不要过度裁剪，否则 Claude 会缺失相关上下文

**模板：**
```gitignore
# 依赖目录
node_modules/
.next/
dist/
build/
vendor/
venv/
__pycache__/

# 构建产物
*.log
*.lock
coverage/
.env*
*.pyc
*.pyo

# IDE 配置
.idea/
.vscode/
*.swp
*.swo

# 大型数据文件
*.csv
*.json
*.xml
*.sql
```

**验证：** 确保 Claude 仍能访问完成任务所需的文件。

### 1.2 CLAUDE.md 压缩

**目标：** 500 token 以内

**结构：**
```markdown
# CLAUDE.md

## Rules
- 规则 1
- 规则 2
- 规则 3
- 规则 4
- 规则 5

## Key Files
- 文件 1: path/to/file1.md
- 文件 2: path/to/file2.md
- 文件 3: path/to/file3.md
```

**原则：**
- 5 条规则 + 3 个文件路径指引
- 项目特定的工作流放在单独文件中
- Claude 只在处理相关内容时才读取链接的文件

**示例：**
```markdown
# CLAUDE.md

## Rules
- 使用 TypeScript 严格模式
- 为每个新函数编写测试
- 遵循现有代码模式
- 使用 ESLint 检查代码风格
- 提交前运行测试套件

## Key Files
- API 路由: src/api/README.md
- 数据库: docs/schema.md
- 样式指南: docs/style-guide.md
```

### 1.3 MCP 服务器管理

**问题：** 每个已连接的 MCP 服务器都增加启动开销，即使未调用。

**操作：**
1. 检查 MCP 列表
2. 断开一周未用的服务器
3. 需要时再重新连接（10 秒操作）

**验证：** 使用 `/mcp` 命令查看当前连接的服务器。

### 1.4 插件管理

**问题：** 活跃插件无论是否调用都增加开销。

**操作：**
- 只保留当前项目使用的插件
- 在设置中禁用未使用的集成

### 1.5 context-mode 安装

**功能：** 开源 MCP 插件，将工具输出路由到沙盒知识库。

**效果：**
- MCP 相关 token 用量降低 50-90%
- 主上下文保持干净
- 需要细节时可搜索已索引内容

**安装：** 参考 context-mode 官方文档

## 二、会话习惯优化

### 2.1 单主题聊天

**原则：** 新主题 = 新聊天，没有例外。

**原因：** 将之前主题的上下文带入新主题是隐形浪费。

**验证：** 每次开始新任务时，检查是否在新会话中。

### 2.2 /clear 和 /compact 使用

| 命令 | 作用 | 使用场景 |
|------|------|----------|
| /clear | 清除整个对话，零上下文 | 完全切换任务 |
| /compact | 摘要对话并重新开始 | 上下文变长但需要保留线索 |

**错误使用：**
- 想用 /compact 时用了 /clear → 需要重新解释上下文
- 想用 /clear 时用了 /compact → 带着旧上下文开始新任务

**Claude.ai 用户：**
- /clear = 开启新聊天
- 没有 /compact 的等价功能

### 2.3 针对特定文件

**避免：**
- "读一下代码库"
- "看一下项目"
- "扫描整个仓库"

**应该：**
- 明确指出相关文件
- 大多数任务只涉及 2-3 个文件

**示例：**
```
❌ "帮我看看这个项目"
✅ "帮我看看 src/api/users.ts 和 src/models/user.ts"
```

### 2.4 用脚本获取数据

**原则：** 如果目的是自己看数据，用脚本而非 Claude。

**原因：**
- read_file 将完整内容永久追加到上下文
- Shell 脚本只返回结果

**示例：**
```
❌ 让 Claude 读取 10000 行日志文件
✅ 用 grep 或 tail 命令提取关键信息
```

### 2.5 CLI 替代 MCP

**原则：** CLI 返回精准、有范围的输出，MCP 将完整响应倾倒到上下文。

**比较：**
- Shell 命令返回 10 行 = 10 token
- MCP 同样请求可能返回 100 倍体量

**判断：** 在默认使用 MCP 之前，先问是否已有 CLI 工具能做这件事。

### 2.6 模型切换

| 模型 | 适用场景 | 相对成本 |
|------|----------|----------|
| Opus | 架构决策、复杂推理、多文件重构、高难度调试 | 高 |
| Sonnet | 实现代码、编写测试、解释代码、日常工作 | 中 |
| Haiku | 重命名、格式化、快速查找、重复性编辑 | 低（Opus 的 1/5） |

**注意：** Haiku 会更快给出错误答案，拿不准时用 Sonnet。

**切换命令：** `/model`

### 2.7 Extended Thinking 控制

**对于不需要深度推理的任务：**
```bash
/effort low
```

**或设置硬性上限：**
```bash
MAX_THINKING_TOKENS=8000
```

**何时不要优化：** 复杂规划、架构决策、多步骤问题分解。

### 2.8 Skills 按需加载

**原则：** Skills 只在显式调用时才加载内容，但 skill 列表在启动时加载。

**规则：**
- 不要调用不需要的 skills
- 不要在会话开始时习惯性调用
- 需要时才加载

### 2.9 子代理使用

**适用场景：** 需要读取超过 3-4 个大文件的任务。

**优势：**
- 子代理在独立会话中运行
- 上下文独立累积
- 完成后权重不影响主会话

**使用方法：** 将高上下文任务委托给子代理。

## 三、架构级优化

### 3.1 会话结构设计

```
主会话（方向把控）
  ├── 子代理1（文件分析）
  ├── 子代理2（代码实现）
  └── 子代理3（测试验证）
```

**原则：**
- 主会话保持干净
- 子代理处理高上下文任务
- 结果返回主会话审查

### 3.2 上下文监控

**会话内监控：**
- 使用 `/usage` 查看当前会话的 token 用量和费用
- 使用 `/cost` 查看预估费用

**跨会话监控：**
- API 用户：访问 console.anthropic.com → Usage
- 订阅用户：访问 claude.ai → Settings → Usage

### 3.3 基线设置

**步骤：**
1. 选择有代表性的任务
2. 记录初始 token 使用
3. 应用优化
4. 运行相同任务
5. 比较差异

**目的：** 没有基线，无从知道是否真的有所改善。

## 四、常见问题解决

### 4.1 账单突然飙升

**可能原因：**
- 缓存问题
- 会话中途切换模型
- 消息间隔过长
- 对话重组导致缓存中断

**解决：**
- 使用 /compact 或新会话
- 检查是否遇到缓存 bug

### 4.2 上下文过载错误

**错误类型：**
- Internal server error (500)：上下文相关
- ECONNRESET/EPIPE：上下文过大导致处理超时
- "Chat has reached its limit"：上下文窗口触顶

**解决：**
- 使用 /compact
- 开始新会话
- 迁移到子代理模式

### 4.3 优化后质量下降

**可能原因：**
- 删除了必要上下文
- 过度压缩重要信息
- 模型选择不当

**解决：**
- 保留关键上下文
- 渐进式优化
- 根据任务复杂度选择模型

## 五、效果衡量

### 5.1 预期节省

**初级优化（一次性设置）：** 降低 20-30%
- .claudeignore
- CLAUDE.md 压缩
- 断开未使用 MCP

**中级优化（会话习惯）：** 降低 40-60%
- 单主题聊天
- 正确使用 /clear 和 /compact
- 针对特定文件
- 模型切换

**高级优化（架构级）：** 降低 60-80%
- 子代理模式
- context-mode
- 自动化监控

### 5.2 监控指标

- Token 消耗量
- 响应时间
- 任务完成质量
- 月度成本

### 5.3 持续改进

**定期检查：**
- 每周查看 token 使用情况
- 每月分析优化效果
- 根据使用模式调整策略

**渐进式优化：**
- 从高优先级开始
- 逐步实施并验证效果
- 根据反馈调整

## 六、禁忌事项

### 6.1 不能牺牲的功能

- 复杂推理任务的 Extended Thinking
- 必要的上下文信息
- 关键的 MCP 服务器
- 任务完成所需的质量

### 6.2 不要过度优化

- 不要在重要决策上节省 token
- 不要删除可能需要的上下文
- 不要为了节省而降低质量
- 不要一次性应用所有优化

### 6.3 不要忽视质量

- 优化是手段不是目的
- 质量优先于成本
- 渐进式优化而非激进改革
- 验证效果后再推广
