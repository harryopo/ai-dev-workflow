# Token 优化完整指南

## 核心机制理解

### Token 消耗的四大来源

1. **工具调用输出（最大消耗源）**
   - 文件读取：完整内容永久追加到上下文
   - Shell 命令：完整输出保留在会话中
   - MCP 服务器：完整 JSON 响应倾倒到上下文
   - 日志文件：数千行日志全部加载

2. **上下文累积**
   - 每条消息都重新读取整个对话
   - 会话越长，每条消息成本越高
   - 较早的上下文权重降低，质量下降

3. **CLAUDE.md 固定基线**
   - 在每条消息之前加载
   - 5000 token 的 CLAUDE.md 每轮消耗 5000 token
   - 是始终背负的固定成本

4. **Extended Thinking**
   - 按输出 token 计费
   - 默认预算可能达到数万 token
   - 复杂任务需要，简单任务不需要

## 优化策略分层

### 第一层：一次性设置（最高 ROI）

#### 1. 创建 .claudeignore

```gitignore
# 依赖目录
node_modules/
.next/
dist/
build/
vendor/
venv/
__pycache__/

# 构建产物
*.log
*.lock
coverage/
.env*
*.pyc
*.pyo

# IDE 配置
.idea/
.vscode/
*.swp
*.swo

# 大型数据文件
*.csv
*.json
*.xml
*.sql
```

#### 2. 压缩 CLAUDE.md

**目标：500 token 以内**

```markdown
# CLAUDE.md

## Rules
- 使用 TypeScript 严格模式
- 为每个新函数编写测试
- 遵循现有代码模式

## Key Files
- API 路由: src/api/README.md
- 数据库: docs/schema.md
- 样式指南: docs/style-guide.md
```

**原则：**
- 5 条规则 + 3 个文件路径指引
- 项目特定的工作流放在单独文件中
- Claude 只在处理相关内容时才读取

#### 3. 断开未使用的 MCP 服务器

每个已连接的 MCP 服务器都增加启动开销，即使未调用。

**操作：**
- 检查 MCP 列表
- 断开一周未用的服务器
- 需要时再重新连接（10 秒操作）

#### 4. 禁用未使用的插件

活跃插件无论是否调用都增加开销。

**操作：**
- 只保留当前项目使用的插件
- 在设置中禁用未使用的集成

#### 5. 安装 context-mode

开源 MCP 插件，将工具输出路由到沙盒知识库。

**效果：**
- MCP 相关 token 用量降低 50-90%
- 主上下文保持干净
- 需要细节时可搜索已索引内容

### 第二层：会话习惯

#### 1. 每个聊天只讨论一个主题

将之前主题的上下文带入新主题是隐形浪费。

**规则：**
- 新主题 = 新聊天
- 没有例外
- 适用于所有 Claude 接口

#### 2. 正确使用 /clear 和 /compact

| 命令 | 作用 | 使用场景 |
|------|------|----------|
| /clear | 清除整个对话，零上下文 | 完全切换任务 |
| /compact | 摘要对话并重新开始 | 上下文变长但需要保留线索 |

**错误使用：**
- 想用 /compact 时用了 /clear → 需要重新解释上下文
- 想用 /clear 时用了 /compact → 带着旧上下文开始新任务

#### 3. 针对特定文件而非整个仓库

**避免：**
- "读一下代码库"
- "看一下项目"

**应该：**
- 明确指出相关文件
- 大多数任务只涉及 2-3 个文件

#### 4. 用脚本获取数据

如果目的是自己看数据，用脚本而非 Claude。

**原因：**
- read_file 将完整内容永久追加到上下文
- Shell 脚本只返回结果

#### 5. 用 CLI 替代 MCP

CLI 返回精准、有范围的输出。MCP 将完整响应倾倒到上下文。

**比较：**
- Shell 命令返回 10 行 = 10 token
- MCP 同样请求可能返回 100 倍体量

#### 6. 切换模型控制成本

| 模型 | 适用场景 | 相对成本 |
|------|----------|----------|
| Opus | 架构决策、复杂推理、多文件重构 | 高 |
| Sonnet | 实现代码、编写测试、日常工作 | 中 |
| Haiku | 重命名、格式化、快速查找 | 低（Opus 的 1/5） |

**注意：** Haiku 会更快给出错误答案，拿不准时用 Sonnet。

#### 7. 限制 Extended Thinking

```bash
# 对于不需要深度推理的任务
/effort low

# 或设置硬性上限
MAX_THINKING_TOKENS=8000
```

**何时不要优化：** 复杂规划、架构决策、多步骤问题分解。

#### 8. 按需加载 Skills

Skills 只在显式调用时才加载内容，但 skill 列表在启动时加载。

**规则：**
- 不要调用不需要的 skills
- 不要在会话开始时习惯性调用
- 需要时才加载

#### 9. 使用子代理

将高上下文任务委托给子代理。

**优势：**
- 子代理在独立会话中运行
- 上下文独立累积
- 完成后权重不影响主会话

**适用场景：** 需要读取超过 3-4 个大文件的任务。

### 第三层：架构级优化

#### 1. 会话结构设计

```
主会话（方向把控）
  ├── 子代理1（文件分析）
  ├── 子代理2（代码实现）
  └── 子代理3（测试验证）
```

**原则：**
- 主会话保持干净
- 子代理处理高上下文任务
- 结果返回主会话审查

#### 2. 上下文管理脚本

```bash
#!/bin/bash
# 会话开始时检查上下文状态
claude -p "/usage" | grep -E "token|cost"
```

#### 3. 自动化监控

定期检查 token 使用情况：
- 使用 `/cost` 查看当前会话
- 访问 console.anthropic.com 查看历史
- 记录基线并比较优化效果

## 常见问题解决

### 问题 1：账单突然飙升

**可能原因：**
- 缓存问题
- 会话中途切换模型
- 消息间隔过长
- 对话重组导致缓存中断

**解决：**
- 使用 /compact 或新会话
- 检查是否遇到缓存 bug

### 问题 2：上下文过载错误

**错误类型：**
- Internal server error (500)：上下文相关
- ECONNRESET/EPIPE：上下文过大导致处理超时
- "Chat has reached its limit"：上下文窗口触顶

**解决：**
- 使用 /compact
- 开始新会话
- 迁移到子代理模式

### 问题 3：优化后质量下降

**可能原因：**
- 删除了必要上下文
- 过度压缩重要信息
- 模型选择不当

**解决：**
- 保留关键上下文
- 渐进式优化
- 根据任务复杂度选择模型

## 最佳实践总结

1. **控制进入上下文的内容**
   - 使用 .claudeignore
   - 压缩 CLAUDE.md
   - 断开未使用的服务

2. **控制会话累积**
   - 单主题聊天
   - 正确使用 /clear 和 /compact
   - 针对特定文件

3. **控制工具输出**
   - 用 CLI 替代 MCP
   - 用脚本获取数据
   - 使用 context-mode

4. **架构级设计**
   - 子代理模式
   - 模型切换
   - 自动化监控
