## 一、关键前置发现：缺陷清单的"编排层"定位需要修正

缺陷清单 X-D16 写的是"`multi_search()` 的形参表（`scripts/search.py:1372-1378`）只有 8 个参数"。
**实测这条定位不准**，v6 主入口根本不调 `multi_search`。

| 路径 | 调用方 | 现状 |
|------|--------|------|
| `search.py:1372` `multi_search()` | 仅 `search.py` 自己的 CLI | 遗留 v3 兼容入口，走 13 个旧引擎（`duckduckgo`/`bing`/`baidu`/…），不经过 Registry |
| **`research.py:816`**（`--all` 模式） | v6 主入口 | `engine.search(args.query, max_results=args.limit)`，**无任何 kwargs** |
| **`research.py:843`**（降级链模式） | v6 主入口 | 同上，**无任何 kwargs** |

`research.py` 全文 `search_depth` 出现 **0 次**——X-D17 判断正确。
`research.py` 走 `registry.get_fallback_chain()` 调度 `engines/` 下的 32 源，`multi_search` 是另一条不相干的旧路。

**结论**：X-D16/X-D17 的真实现落点是 `research.py:816` 与 `:843` 两处调用点，不是 `multi_search` 的形参表。
`multi_search` 本轮**不改**（它服务的是 `search.py` CLI，改它属于扩大范围）。

### 1.1 透传安全性（已实测，不存在风险）

`grep "def search" engines/*.py` 全部 28 处实现的签名统一为：

```python
def search(self, query: str, max_results: int = 10, **kwargs) -> Optional[List[SearchResult]]:
```

基类契约（`base.py:106`）同样带 `**kwargs`。**所有引擎都吞得下多余 kwargs**，透传不会 TypeError。
消费方实测：

| 参数 | 消费位置 | 现状 |
|------|----------|------|
| `search_depth` | `mcp_engines.py:157` | `kwargs.get("search_depth", "basic")` — 永远取默认值 |
| `days` | `mcp_engines.py:160-161` | `if "days" in kwargs` — 编排层从不传 |
| `include_domains` | `mcp_engines.py:162-163` | 同上 |
| `exclude_domains` | `mcp_engines.py:164-165` | 同上 |
| `include_raw_content` | `mcp_engines.py:158` | `kwargs.get(..., False)` — 硬编码默认 |
| `time_range` | `fallback.py:653-654`（SearXNG） | `if 'time_range' in kwargs` |
| `days` | `skill_engines.py:313` | `kwargs.get("days", 30)` 写死默认 |

下游全部就位，只等编排层传值。

## 二、管道层：X-D16 + X-D17

### 2.1 统一构造 kwargs

在 `cmd_search` 内新增一个 helper，只在参数非 `None`/非空时塞入，保证不带参数时**请求体与改动前逐字节一致**：

```python
def _build_engine_kwargs(args, search_depth) -> Dict[str, Any]:
    """把编排参数转成引擎 kwargs。未显式指定的键一律不出现，
    让引擎保持自己的默认值（不传 ≠ 传空值）。"""
    kw: Dict[str, Any] = {}
    if search_depth:
        kw['search_depth'] = search_depth
    tr = getattr(args, 'time_range', '') or ''
    if tr:
        kw['time_range'] = tr
    inc = [d.strip() for d in (getattr(args, 'include_domain', '') or '').split(',') if d.strip()]
    if inc:
        kw['include_domains'] = inc
    exc = [d.strip() for d in (getattr(args, 'exclude_domain', '') or '').split(',') if d.strip()]
    if exc:
        kw['exclude_domains'] = exc
    return kw
```

`--include-domain` / `--exclude-domain` 用 `action='append'`（可重复），落进列表；
`--time-range` **已存在**（`research.py:1181`，argparse dest 自动转 `time_range`），
当前只喂给 `plan.generate_plan`（`:714`）而没下发给引擎——本轮只是把它接下去，**不新增参数**。

### 2.2 X-D17：Tavily 检索深度接线

**歧义消除**：`research.py --depth` 是"子问题数量档位"（`quick/standard/deep/extreme`），
`search.py --depth` 是"Tavily 检索深度"（`basic/advanced`）。两者同名不同义。

改法（按缺陷清单建议，但调整优先级）：

1. **新增** `--search-depth`，`choices=['ultra-fast','fast','basic','advanced']`（补齐 Tavily 真实 4 档）
2. **不传时由 effort 推导**，而不是要求用户手动指定。推导基准是
   `plan.resolve_preset_key()` 的**归一后** preset key（注意 `exhaustive` 归一为 `extreme`，
   直接拿 effort 原词查表会落空）：
   ```
   quick    → fast
   standard → basic
   deep     → advanced
   extreme  → advanced
   ```
   理由：缺陷清单说这是"准确度最便宜的一个杠杆"，让用户每次手填等于白给。
3. `--search-depth` 显式传入时覆盖推导值
4. 文档层在 SKILL.md 标注两者语义差异，不重命名 `--depth`（改名会破坏既有调用方与 SKILL.md 全部示例）

### 2.3 缓存 key 必须扩维

`research.py:673-680` 的 `LRUCache.make_key()` 现有维度：query/sources/language/region/depth/ledger/effort/breadth/perspectives/reflect_rounds。
**必须追加** `search_depth` / `time_range` / `include_domain` / `exclude_domain`，
否则改了这四个参数重跑会命中旧缓存——这正是 v6.3 踩过的坑（`--ledger` 二跑账本为空）。

### 2.4 两处调用点同步改

`research.py:816`（`--all`）与 `:843`（降级链）都改成：

```python
results = engine.search(args.query, max_results=args.limit, **engine_kwargs)
```

## 三、策略层：X-D18 + X-D20

### 3.1 X-D18：每个子问题生成 3~5 条分类型查询词

**现状**：`SKILL.md:318-335` Phase 2.5 是"1 子问题 = 1 条查询"，
`SubQuestion.keywords` 只有单个维度名，`ResearchPlan` 无分类型查询结构。

**改法**：`plan.py` 新增 `SearchQuerySet` 数据结构 + 生成器。

```python
QUERY_FACETS = {
    'fact':    {'suffix': '原理 是什么 机制',        'cures': '基础面'},
    'data':    {'suffix': '2026 占比 排名 基准测试',  'cures': '缺量化'},
    'counter': {'suffix': '失败 缺陷 批评 反例',      'cures': '只搜到吹的'},
    'fresh':   {'suffix': '发布 更新 最新 2026',      'cures': '引用过期'},
    'primary': {'suffix': 'site:gov site:edu filetype:pdf 原文 报告', 'cures': '二手转述污染'},
}
```

`SubQuestion` 增加字段 `query_facets: List[Dict]`（每项含 `facet` / `query` / `curation`），
`to_dict()` 一并输出。**类型化而非同义改写**——同义改写等于白搜。

条数上限 3~5：LangChain 开源 DR 实证消融的 `Nquery=3` 附近最优，超过是噪声。
按 `resolve_preset_key()` 归一后的 preset key 定档：
`quick=3` / `standard=4` / `deep=5` / `extreme=5`
（`extreme` 多轮而非单轮加量，所以与 `deep` 同为 5）。

**backfill 约束**：从 `plan.json` 反序列化旧计划时，`query_facets` 缺失必须能正常工作（给 `default_factory=list`），
不得让旧 session 无法续跑。

### 3.2 X-D20：检索算子进查询生成层

**现状实测**：`site:` 全仓只有 3 处，全在 `cn_sources.py` 引擎失败时的自我兜底（`:109/:251/:316/:431`）。
`exact_match`（Tavily 逐词精确匹配）**0 命中**。查询生成层从未被告知可用算子。

**改法**：
1. `QUERY_FACETS['primary']` 模板自带 `site:` / `filetype:` —— 算子由此进入生成层，不是靠文档口头告知
2. SKILL.md Phase 1 生成查询词处加算子白名单说明，**硬约束：一条查询最多 1 个算子**，
   避免过度收窄导致 0 结果（这会直接推高 `--probe` 的"⚠️ 0 结果"比例）
3. 边界：算子只在 `primary` 类查询用；`fact`/`data`/`counter`/`fresh` 不加（加了收窄过头）

## 四、门禁层：X-D19 + X-D21

### 4.1 X-D19：走 A 方案（轻量）

**决策记录**：缺陷清单 B 方案（"进账本来源必须过一次全文抓取"）与
`论文-安全章节-注入防护方案.md` S.6 的硬约束直接冲突——S.6 写明"X-D19 不得早于 L1+L2 上线"，
因为全文比摘要长约 100 倍，可藏载荷位置成倍增加。

本轮选 **A 方案**：`mcp_engines.py:158` 的 `include_raw_content` 默认改 `True`。

这样做的理由：A 方案不新增全文抓取链路，不放大注入面，S.6 的约束不触发；
同时把 MCP 路径的默认行为改对。全文抓取的 B 方案留待 L1/L2 落地后单独评估。

**注意**：默认改 True 会增大响应体。必须确认 `include_raw_content` 进缓存 key，
否则不同 effort 复用同一缓存条目。`_build_search_result` 需要能处理正文更长的情况
（字段截断，见下）。

### 4.2 X-D21：纯规则筛查高风险 claim

**决策记录**：不做 LLM 判定（会破坏 `--stamp` 的可复现性，且校验门从确定性脚本变成依赖模型调用的不确定环节）；
不改账本 schema 加引文字段（影响面太大）。

**改法**：`validate_report.py` 新增筛查步骤，只挑出**高风险 claim**交 Lead 定夺。

三类高风险模式（脚本判定，零 token 成本）：

| 模式 | 判据（确定性规则） | 治什么 |
|------|-------------------|--------|
| 定量 | 含数字 + 单位/百分比/倍数（`\d+(\.\d+)?%`、倍数词） | 数字被引申或记错 |
| 绝对化 | 全部/所有/总是/从不/唯一/最/第一/彻底/必然 | 过度断言 |
| 比较级 | 比…更/优于/胜过/远超 + 比较对象 | 无基准的比较 |

**处置**：命中的 claim **不自动删除、不自动降级**——脚本标记为 `needs_support_check`，
在 `stats` 里报数量，并打印 claim id + 命中原因，让 Lead 在 Phase 3.5 逐条定夺。
理由与 L3 不可信标记同理：只降级不删除，避免攻击者/噪声故意植入特征词来躲避（DoS-by-poisoning）。

**不阻断 `--stamp`**：这是"提醒 Lead 要查"，不是"证明 Lead 没查"。
真要阻断需要 LLM 判定，那条路本轮明确不走。

**边界声明**：本项是"筛出待查清单"，**不是**"验证引用支持 claim"。
漏检率不可控，须在 SKILL.md 与 CHANGELOG 写明这一点，不得宣称"已实现支持度回查"。
