## 零、先做一条更正（防止主任务去修一个不存在的问题）

我在口头汇报时说过「多后端是降级关系，不是并集关系」。**这句是错的。**

实测：`scripts/search.py:1466-1480` 对单次查询用 `ThreadPoolExecutor(max_workers=len(available))`
把**所有可用引擎并行打一遍**，再 `all_results.extend(...)` 汇成一个结果池。这是并集，不是级联降级。
四层级联描述的是**引擎怎么选进来**，不是**选进来后怎么调用**。

→ **本批不设这条缺陷。** 请勿为此改动 `router.py` 的级联逻辑。

## 一、缺陷清单

### 🔴 X-D16 编排层断链：四个关键检索参数在引擎层已支持，却永远收不到值

**现象**：`multi_search()` 的形参表（`scripts/search.py:1372-1378`）只有
`query / max_results / sources / search_depth / auto_detect / use_cache / min_score / enable_iterative`。

而下游是**收得到**的：

| 参数 | 下游已支持位置 | 编排层能否传到 |
|---|---|---|
| `include_domains` | `engines/mcp_engines.py:162-163` | ❌ 无入口 |
| `exclude_domains` | `engines/mcp_engines.py:164-165` | ❌ 无入口 |
| `days` | `engines/mcp_engines.py:160-161`、`skill_engines.py:313`（默认 30 写死） | ❌ 无入口 |
| `time_range` | `engines/fallback.py:653-654` | ❌ 无入口 |
| `include_raw_content` | `engines/mcp_engines.py:158` | ⚠️ 硬编码默认 `False` |

**影响**：
- 秘塔式「信源黑白名单」只能**事后**靠 Tier 打分降权，无法**前置**排除 → SEO 农场、内容农场照样进结果池、照样占 `max_results` 名额
- 时效类调研（"最新""2026 年"）拿不到时间窗过滤 → 会引过期资料
- `exclude_domains` 缺失使「已知不该看的源」每次都重新污染一遍

**改法**：给 `multi_search()` 增加 `time_range`、`include_domains`、`exclude_domains` 三个透传形参，
非 `None` 时才塞进 `kwargs`（保持现有引擎签名不变，避免动 16 个引擎）。
CLI 对应加 `--time-range`（search.py 侧，注意与 research.py 已有同名参数语义统一）、`--include-domain`、`--exclude-domain`（可重复）。

**验收**：`python search.py "测试" --exclude-domain csdn.net --time-range month` 的 HTTP 请求体里能看到对应字段；
不带参数时请求体与改动前逐字节一致（不回归）。

### 🔴 X-D17 主入口 research.py 完全碰不到 Tavily 检索深度，且档位数不对

**现象**：
- `research.py:1160-1162` 的 `--depth` 语义是**子问题数量**（`quick/standard/deep/extreme`）
- `search.py:1812-1814` 的 `--depth` 语义是 **Tavily 检索深度**（`basic/advanced`）
- 两个同名参数不同语义；research.py 全文 `search_depth` 出现 **0 次**

**影响**：v6 主入口跑的所有调研，Tavily 一律走 `basic`。关键子问题（定量数据、争议核对）
拿不到 advanced 的跨索引重排——而这是**准确度最便宜的一个杠杆**。
另外 Tavily 实际有 4 档（`ultra-fast / fast / basic / advanced`），`choices` 只给了 2 档，
废查询省不下 credits。

**改法**：
1. 把 research.py 的 `--depth` 重命名为 `--sub-issues`（或保留但文档显著区分），消除同名歧义
2. research.py 新增 `--search-depth`，由 `effort` 推导默认值：`minimal/light→fast`、`standard→basic`、`deep/exhaustive→advanced`
3. `search.py:1813` 的 `choices` 补齐为 4 档

**验收**：`--effort exhaustive` 时日志打印实际下发的 Tavily `search_depth=advanced`；
缓存 key 含该维度（`search.py:1402` 已把 depth 纳入 key，确认新参数不串缓存）。

### 🔴 X-D18 广度只有一维（子问题数），缺「同一子问题按信息需求类型扇出」

**现象**：
- `SKILL.md:318-335` Phase 2.5：每个子问题 spawn 一个子 Agent，子 Agent 执行一次
  `research.py "{subtopic}"` —— **1 子问题 = 1 条查询**
- 广度参数 `research.py:520`：`{'quick':2,'standard':4,'deep':8,'exhaustive':12}`，控的是**子问题个数**

所以当前总查询数 = 子问题数 × 并行引擎数。**「换个问法再搜一次」这一维完全不存在。**

**影响**：这是广度的真正闸门，也是本批收益最大的一条。单一表述只能命中一种信息需求：
`X 框架 对比` 搜不出「X 的失败案例」，也搜不出「X 官方架构文档」。子问题拆得再细，
每个子问题仍被一条查询的表达方式锁死 → 报告表现为「每个点都提到了，但数据面/反方面/原始文档面普遍薄」。

**改法**：在 Phase 2.5 子 Agent 指令里，把「1 条检索」改为「按 5 类互补信息需求各出 1 条」，
且**类型化而非同义改写**（同义改写等于白搜）：

| 类型 | 模板示意 | 治什么病 |
|---|---|---|
| 事实/定义 | `<子问题> 原理 是什么` | 基础面 |
| 数据/排名 | `<子问题> 2026 占比 排名 基准测试` | 缺量化 |
| 争议/反方 | `<子问题> 失败 缺陷 批评 反例` | **只搜到吹的** |
| 时间线/最新 | `<子问题> 发布 更新 2026` + X-D16 的时间窗 | 引用过期 |
| 原始文档 | `site:gov site:edu filetype:pdf <子问题>` | 二手转述污染 |

条数上限 **3~5 条/子问题**，不要更多——见第三节行业依据。
已有的 `--perspectives 3`（`SKILL.md:236` 对抗视角）是**评估视角**，不是**检索视角**，两者不重复，
建议映射关系写成：怀疑者视角 → 强制发「争议/反方」查询。

**验收**：`--plan-only` 输出的计划里能看到每个子问题的 3~5 条分类型查询词；
实跑 `evidence.jsonl` 中同一子问题的来源域名互斥度（去重后独立域名数）明显上升。

### 🟠 X-D19 走 MCP-Tavily 时默认只拿到摘要，证据可能建立在 snippet 上

**现象**：`engines/mcp_engines.py:158` — `"include_raw_content": kwargs.get("include_raw_content", False)`

**影响**：与 `SKILL.md:336` v6.10 的约束（"`--ledger` 只登记证据，不再把搜索结果的标题写成 claim"）
方向一致，但只挡住了「拿标题当结论」。若正文内容也来自 snippet 而非抓取全文，
CRAAP 评分和 claim 支持度判断就都在**摘要**上做——摘要会漏限定条件、会把"有研究显示"变成"定论"。

**改法**：两条选一，不要都做
- **A（轻）**：MCP 路径把 `include_raw_content` 默认改 `True`，并纳入 cache key
- **B（重，推荐）**：在子 Agent 指令里写明——**进账本的来源必须过一次全文抓取**
  （Tavily extract / Firecrawl scrape / `defuddle` / crawl4ai 任一），摘要只用于筛选，不落 claim

B 与现有 `academic_fulltext.py`、crawl4ai 引擎是同一条脉络，不新增依赖。

**验收**：抽查 `evidence.jsonl`，每条 claim 的来源记录里能区分
「正文来自 snippet」还是「正文来自 extract」，后者占比 ≥90%。

### 🟠 X-D20 `site:` 等检索算子只在降级路径内部自用，没进查询生成层

**现象**：全仓 `site:` 的使用只有三处，且都是**引擎失败时的自我兜底**：
`cn_sources.py:109`（百度站点限定）、`cn_sources.py:251/316`（搜狗微信失败→转百度 `site:weixin.qq.com`）、
`cn_sources.py:431`（搜狗知乎失败→转百度 `site:zhihu.com`）。

**影响**：查询由 LLM 生成，但生成层从未被告知可以用算子。引号精确短语、`-域名` 排除、
`intitle:`、`filetype:pdf` 这些**免费且高收益**的召回控制手段全部闲置。
`include_raw_content`/`exact_match` 之外，`exact_match`（Tavily 的逐词精确匹配）在仓内 0 命中。

**改法**：在 Phase 1 生成查询词处加一段算子白名单说明（约束：一条查询最多用 1 个算子，
避免过度收窄导致 0 结果）。与 X-D18 的「原始文档」类型天然配套。

**验收**：计划输出中存在含算子的查询；`--probe` 的四级判定里「⚠️ 0 结果」不因滥用算子而上升。

### 🟡 X-D21 缺「支持度回查」：引用存在 ≠ 引用支持该 claim

**现象**：现有链路是 claim → source 溯源（`ledger.py`）+ CRAAP 五维来源可信度评分
（`SKILL.md:1018`）+ 来源 Tier 分级。**评的都是「这个源可不可信」，没有一步评「这句话是否真被这段文字支持」。**

**影响**：Tier 高、CRAAP 高分的来源，配上被过度引申的 claim，照样能全绿过门。
这正是 Perplexity 在 DeepResearch Bench 上 FACT 指标（C.Acc.）领先所对应的能力项。
注意与 v6.10 的区别：v6.10 防的是「标题被当成结论」（登记环节），X-D21 补的是
「正文与 claim 语义是否对得上」（发布前环节）——不重复。

**改法**：发布前校验门里增加一道定向回查：对**定量、绝对化、比较级**三类高风险 claim，
把 claim + 来源正文一起送判「支持 / 部分支持 / 不支持」，不支持则降级为「待证」或删除。
只跑这三类，不要全量（成本会失控）。

**验收**：故意在账本里塞一条来源正文不支持的 claim，校验门必须拦下并给出理由。

| 编号 | 一句话 | 优先级 | 工作量 | 动架构？ |

| X-D17 | 主入口接上 Tavily 检索深度 | 🔴 P0 | 小 | 否 |

先修管道再修策略，否则扇出只会把脏结果乘以 5。

## 三、行业依据（为什么是这几条，不是别的）

1. **每子问题 3 条查询附近最优，超过是噪声。**
   LangChain 的开源 DR 实证消融：去掉分解 / 去掉迭代 / 去掉综合，分数分别掉到 5% / 5% / 0%；
   其调出的配置为每子问题 `Nquery=3`、`k=3`、最大深度 6、单任务约 210 秒。
   → X-D18 定 3~5 条而**不是**越多越好。
2. **换后端就是换分数，单一后端有天花板。**
   同一 BrowseComp 任务：Parallel Basic 53% / Tavily 42% / Exa 40%。
   → 现有并行并集（见第零节更正）是对的；X-D16/X-D17 是让这个并集打得更好。
3. **停止判据行业已收敛为多信号**：覆盖率 + 无高优先级空白 + 边际收益递减 + 逻辑闭环 + 轮次硬上限。
   `reflect.py` 已实现边际收益递减（据 `references/国内大厂深度研究方案调研-v3.md` 记录）。
   → **本批不提"加停止判据"类需求**，避免重复建设。
4. **引用可信度是独立评测轴。** DeepResearch Bench 用 RACE（报告质量）+ FACT（引用可信度）双框架，
   Perplexity 靠 FACT 领先。→ X-D21 的依据。

## 四、明确不建议做的（防止主任务过度设计）

以下几项在 `references/` 旧文档里被列过为"借鉴点"，本轮复核后建议**搁置**：

- ❌ **GRPO / 强化学习改造**（`国内大厂深度研究方案调研-v3.md` 第 3.1 条）
  本 skill 是 prompt 编排层，拿不到训练权。Kimi/通义/OpenAI 的训练型路线与编排型路线是两个物种。
- ❌ **模型即 Agent / 300 轮硬上限**（同上第 1 条）
  宿主 Agent 的 turn 上限不由 skill 决定。`SKILL.md:22` 已记录「子 Agent fork 仅 10 turn」这一硬约束，
  把它写成 300 是空头支票。
- ❌ **多模态爬取 / 音视频调研**（天工 MM-Crawler）——收益不抵工程量，且与「报告为主」的产品定位偏离。
- ❌ **代码解释器子 Agent**（文心一言）——宿主本身能跑 Python，属重复建设。
- ⏸ **登录态爬取**（智谱 AutoGLM）——`anti-bot-research-2026.md` 已深入，涉及凭证与合规，
  单独立项，不要塞进本批。

## 五、本批未覆盖、但值得主任务自己看一眼的两点

1. **`min_score` 与相关性告警的耦合**：`multi_search()` 有 `min_score` 形参（默认 0，即不启用），
   `SKILL.md:1293` 又规定「⚠️ N 条与查询词几乎无重叠时必须换词」。
   前者是硬过滤、后者是人工告警——**建议确认默认 0 是否刻意**（我未深查其设计意图）。
2. **`enable_iterative` 默认 False**（`search.py:1378`）：迭代重搜能力已存在但默认关。
   若 X-D18 的扇出上线，需决定「边想边搜」由 Phase 2.5 子 Agent 负责还是由引擎层 `enable_iterative` 负责，
   **不要两处都开**，会翻倍烧 credits。
