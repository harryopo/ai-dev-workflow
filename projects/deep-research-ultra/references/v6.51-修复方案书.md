## 一、P0：WIP（v6.51.0）的回归与完整性

### P0-1 「一页拍板」必需章节导致根目录 tests/ 3 项失败

**因果链（已逐步验证）**：

1. WIP 给 `validate_report.py` 的 `REQUIRED_SECTIONS` 新增 `'一页拍板'`（validate_report.py:42），缺节即产生 issue（validate_report.py:335-345，v6.50 起连"空壳节"都拦）；
2. WIP 作者同步更新了 `scripts/tests/` 下 5 个测试文件的报告 fixture（test_v6.py、test_v66_fixes.py、test_v615_dogfood.py、test_validation_stamp.py 等，全部加了「一页拍板」节）；
3. **但根目录 `tests/test_server_tools.py` 的 `GOOD_REPORT`（:194 `_report()` 引用）没有该节**——`grep 一页拍板 tests/test_server_tools.py` 为空；
4. 后果：`test_gate_check_reports_pass_and_fail`、`test_stamp_binds_body_and_ledger`、`test_second_claim_after_stamp_invalidates_ledger_match` 三项全部 `assert False`（`drux_stamp_issue` / `gate_check` 的 ok 恒为 False）。

**为什么漏**：测试分布在两个根（`skills/.../scripts/tests/` 内核测试 vs 仓库根 `tests/` 插件壳测试）。改公共门（validate_report）时，作者按惯性只扫了内核测试目录。这不是粗心，是结构必然——见 P1-2。

**修复（T1）**：给 `tests/test_server_tools.py` 的 `GOOD_REPORT` 与 `_sparse_report` 类 fixture 补「一页拍板」节（照抄 `scripts/tests/test_v6.py:186` 的四行格式）。**验收：仓库根 `pytest tests/` 50/50 绿；两处合计 935/935。**

## 二、P1 问题与修复

### P1-1 宣传页大数字 32 vs 注册表 34

**证据**：`index.html` meta 区 `<div><strong>32</strong><span>数据源 · 四层</span></div>`；SKILL.md 三处写「34 个数据源」且 `test_v6410_source_count_pin.py` 把 SKILL.md 文本钉死在注册表实测值上（该测试绿 → 注册表真实值 = 34）。

**为什么钉子没抓住**：`test_landing_page_facts.py` 对 index.html 只钉了两类模式——`<span class="chip">` 数量对撞注册表、以及「本机可用 N 个」类禁印声明。**meta 区的大数字 `<strong>N</strong>` 不在任何钉子正则里**，而它恰恰是手抄旧文案的高发位（该文件 docstring 自己就记录过"30 个数据源""20/32"两代漂移史）。

**修复（T2）**：
1. `index.html` 大数字 32 → 34；
2. `test_landing_page_facts.py` 增一条钉子：抽取 meta 区所有 `<strong>\d+</strong>` 中与「数据源」文案相邻的那个，与 `build_registry()` 对撞。只钉这一个，不做全页数字推断（页面上还有测试数、版本号等各有主人的数字，见「明确不做」）。

### P1-2 测试双根结构 → 防漏措施

内核测试（`scripts/tests/`，885 项）与插件壳测试（根 `tests/`，50 项）分属两层，但 `validate_report.py` 这类公共模块两边都消费。本次 P0-1 就是结构漏损的第一案发。

**修复（T3，二选一，推荐 a）**：
- **a. 全仓测试入口**：仓库根加一条薄脚本（或 Makefile/npm script），固定依次跑 `scripts/` 与 `tests/` 两个套件并汇总计数，CHANGELOG 的「全量 N 项」一律以它为准。成本低，不动现有布局。
- b. 合并目录。不推荐：两套测试的 fixture 语义不同（壳测试走 `server.*` 工具层），合并会制造伪耦合。

**验收**：任何人在仓库根跑一条命令能看到真实总数；P0-1 类回归在该命令下必然暴露。

### P1-3 工作区镜像治理

镜像停在 v6.15.0（35 版前），`scripts/engines/mcp_client.py` 还是 v4.0 世代实现，其 `test_mcp_client.py::test_no_orphan_after_timeout` 的 `TypeError: argument of type 'NoneType' is not iterable`（镜像 tests:186）在主线早已随 `mcp_client.py` 重写消失——**不值得在旧镜像上修**。真正的问题是它继续存在会误导（本次对话前段就被它带偏过一次）。

**修复（T4）**：
1. 把 `references/搜索准确度与广度缺陷清单.md`、`references/论文-安全章节-注入防护方案.md` 提交进工作区库（这两份是 v6.15 的输入文档与后续安全路线图，有存档价值）；
2. 镜像二选一：**(a)** 删除 `projects/deep-research-ultra`，在 README/工作区文档留一行指向开发库与 GitHub 远端；**(b)** 保留但在目录内加 `STALE.md` 声明"只读存档，主线在 ~/.zcode/skills/deep-research-ultra 与 github.com/harryopo/deep-research-ultra"。推荐 (b)，保留历史快照成本为零，风险是再被当成主线——所以 STALE.md 要放目录根部第一眼位置。

### P1-4 注入防护 L1/L2/L4 启动（技术债里唯一"路线级"的）

《论文-安全章节-注入防护方案》S.2 的诚实结论是输入侧零防护；S.9 的工作量表明确：**L1 出口白名单（`engines/base.py` 单点收口，小）+ L2 证据结构化隔离（中）+ L4 canary（小）低成本高收益，建议立刻做，不等论文**；且 L1+L2 是 X-D19 B 方案（进账本前全文抓取）的前置条件——这条链不解开，v6.15 留下的"证据可能建立在 snippet 上"的 B 方案就只能永远停在其 A 方案。

**修复（T5，排期建议而非本轮实施）**：顺序 L1 → L4 → L2 → 复评 X-D19 B 方案 → S.7 评测语料（大工程，单独立项）。每步落一个版本号，沿用"边界与代价"节惯例写清暴露面变化（v6.15 CHANGELOG 已预警：扇出 ×3~5 与安全是同一条曲线的两端）。

## 五、明确不做的（防过度设计）

1. **不合并两个测试根**——壳测试与内核测试语义不同，合并制造伪耦合（见 P1-2 方案 b 的否决理由）。
2. **不给 index.html 全页数字做通用推断钉子**——测试数、版本号等数字各有自己的主人（test_v6410 钉 SKILL.md、T2 只补数据源大数字），通用推断会变成脆弱的全页正则。
3. **不在旧镜像上修任何 bug**——镜像的唯一正确处置是存档化（T5）。
4. **hedge 词表不做大规模扩充**——误伤率随词表增长，等英文报告实跑需求出现再补。
5. **L3/L5 注入防线本轮不启动**——L3 依赖账本 schema 变更（与 P2-6 同批），L5（高危动作二次确认）与调研场景耦合度待评估，均按 S.9 的阻塞关系排队。
