# 双轴记忆模型 · 详细方案书

> 版本 v1.0（2026-10-31） · 决策人：harryopo
> 一句话：super-memory 解决"agent 怎么接住活"（项目轴），四层架构解决"agent 怎么懂你"（用户轴）——**正交两轴，在核心块交汇**。本方案书设计两轴的融合路径。

---

## 一、两轴的发现（为什么需要双轴）

### 1.1 现有体系只覆盖了项目轴

super-memory 的五落点模型（.learnings 暂存 → HANDOFF 交接 → .ai/knowledge 长期 → 宿主记忆库 → 规则文件）回答的是：**"这个项目做得怎么样、怎么接"**。它有三轮 dogfood 验证、19/19 评测、完整门禁——在项目维度已经很完整。

但它对**用户维度**只有一层平铺的"宿主记忆库"（user-profile / 协作偏好 / 工作方式散在 MEMORY.md 里）——没有加工管线、没有分层、没有常驻机制。结果是：agent 每次开场要靠 hook 提醒去"读"，而不是**自动就懂**。

### 1.2 四层架构补的正是用户轴

市面用户记忆产品（ChatGPT Memory、Letta core blocks、Mem0 原子事实）的共性架构是一个**加工管线**：

```
原始对话 → 原子事实提取 → 场景聚合 → 核心记忆块（常驻上下文）
```

越往后越浓缩、越常驻、越"懂你"。super-memory 缺的正是这条管线。

### 1.3 两轴在三个点交汇

| 交汇点 | 项目轴提供 | 用户轴提供 |
|---|---|---|
| 开场注入 | §0 快照（项目状态） | 核心块（用户画像/偏好/协作方式） |
| 保存入口 | capture/handoff（项目记忆） | capture 同时写用户轴（偏好类） |
| 检索 | 四层检索（项目知识） | Tags + 排序（用户偏好） |

## 二、四层架构开源对标（每层的借鉴来源与取舍）

### 2.1 原始对话层

| 系统 | 做法 | 借鉴判断 |
|---|---|---|
| OpenCode | 会话 jsonl 落盘，压缩时读 | **不重复做**——宿主已在管，super-memory 只在 capture 时提取 |
| ChatGPT Memory | 对话原文存储 + 后台提取 | 同上 |
| **结论** | 原始对话由宿主管；本方案只做"从对话提取"的入口（capture 已是） | 零改动 |

### 2.2 原子记忆层（借鉴 Mem0）

| Mem0 做法 | 本方案借鉴 | 差异 |
|---|---|---|
| LLM 从对话抽取"候选原子事实" | capture 的 Summary 字段强制写成独立成立的原子事实 | 不用 LLM 二次抽取——写入时人/agent 直接写原子 |
| ADD/UPDATE/DELETE/NOOP 四操作由 LLM 判定 | 四操作由 agent 判定（同源），但 DELETE 替换为 SUPERSEDE 降级留痕 | 不删除（本项目铁律） |
| embedding 相似度检索旧记忆 | grep + Tags 检索（单人规模 BM25 够用） | embedding 为 opt-in 第三层 |

**关键借鉴**：**"一条记忆 = 一个原子事实"的写入纪律**。当前 capture 的 Summary 字段常写成复合句（"讨论了部署和测试"）——改为强制原子化："每条记忆的 Summary 必须独立成立、可单独检索、可单独失效"。这不是格式变化，是**写入措辞纪律**。

### 2.3 场景记忆层（借鉴 A-Mem）

| A-Mem 做法 | 本方案借鉴 | 差异 |
|---|---|---|
| 新记忆入库时自动生成与旧记忆的链接，旧记忆被"演化更新" | Related 互链已有——补**场景聚合视图**：同 Tags 条目聚合成"场景包" | 不自动演化（防 over-generalization），聚合靠 Tags 检索 |
| Zettelkasten 卡片盒：知识自然生长 | Tags 受控词表 + 场景包命名规范 | 单人场景不需要自动链接生成（LLM 判定成本高），Tags 够用 |

**关键借鉴**：**场景包是 Tags 的聚合视图，不是新存储结构**。同 Tags 的条目天然构成一个场景包——`search.py "部署"` 已经能聚合。缺的只是：**给 Tags 加受控词表**（领域词从 Area 取，英文词用固定枚举），避免同义散落。

### 2.4 核心记忆层（借鉴 Letta/MemGPT）

| Letta 做法 | 本方案借鉴 | 差异 |
|---|---|---|
| Persona + Human 两个 block，**始终在 system prompt 里**，agent 通过工具 self-edit | 核心块由 hook **开场注入**（不占 system prompt，走 SessionStart 输出） | 注入式而非常驻式——单人场景 token 预算有限，注入比常驻更灵活 |
| agent 用 core_memory_append/replace 工具 self-edit | 核心块由 save/neat 维护，**不由 agent 在对话中自动改写** | 防 over-generalization（auto-memory 的社区教训） |
| 存储在 Postgres/SQLite | 存储在宿主记忆库的 Markdown 文件（user-profile.md + 协作偏好.md + 当前项目.md） | 纯文件，人可直接读 |

**关键借鉴**：**核心块的内容来源与注入方式**。核心块 = 从宿主记忆库精选的 3-5 个条目的 description 行（每行 ≤ 80 字），拼成 ≤ 500 字的 always-in-context 摘要——由 hook_session_intro.py 在开场时自动读取并注入。

## 三、融合设计：改什么、怎么改

### 3.1 super-memory skill 层改动（纯 Markdown 纪律，零依赖）

| # | 改什么 | 文件 | 改法 |
|---|---|---|---|
| S1 | capture 加**原子化措辞规则** | subskills/capture/SKILL.md | Summary 字段规则加一句："**原子化**：Summary 必须独立成立、可单独检索、可单独失效——不写复合句、不写'今天讨论了X'类叙事" |
| S2 | 核心块定义 | references/memory-addressing.md | 新增"核心块"小节：从宿主记忆库精选 3-5 条（用户画像 / 协作偏好 / 当前项目一句话），每条取 description 前 80 字，拼成 ≤ 500 字注入块 |
| S3 | hook_session_intro.py 加核心块注入 | scripts/hook_session_intro.py | 在 §0 快照之前，读取核心块（宿主记忆库路径的 user-profile.md 等 3 条的 description），打印 `── 核心记忆（来自宿主记忆库）──` |
| S4 | 检索过滤失效条目 | scripts/search.py | `score_file()` 加一条：含 `**已失效**` 的条目得分 ×0.1（不排除——留痕有价值，但降权） |
| S5 | 受控 Tags 词表 | references/memory-doctor.md | Tags 领域词建议从 Area 字段取（frontend/backend/infra/tests/docs/config），英文词从固定枚举取；doctor 检查六顺带列出 Tags 不在词表内的条目 |

### 3.2 agent-memory 工具层改动（core 扩展，opt-in）

| # | 改什么 | 文件 | 说明 |
|---|---|---|---|
| T1 | `core/memory_block.py` | 新增 | `build_core_block(user_memory_root) -> str`：读 user-profile.md / 协作偏好.md / 当前项目.md 的 description 行，拼成核心块。供 hook / MCP / CLI 调用 |
| T2 | `core/atomize.py` | 新增 | `atomize(text) -> [str]`：把块式条目的 Summary 拆成原子事实列表（基于句号/分段切分，不用 LLM）；`is_atomic(summary) -> bool`：判断是否原子（不含"和/与/然后"等复合连接词） |
| T3 | `core/scene.py` | 新增 | `scene(root, tag) -> [Entry]`：按 Tag 聚合场景包；`scene_list(root) -> [(tag, count)]`：列出全部场景 |
| T4 | `core/decay.py` | 远期 | 衰减/强化：基于使用统计（哪条被检索命中过）调整置信度与排序权重 |

### 3.3 不改的

- super-memory 六子命令结构不变（capture/handoff/intake/save/neat/promote）
- 数据格式 schema 不变（Tags 已有，原子化是措辞纪律不是新字段）
- 宿主记忆库文件格式不变（user-profile.md 等已在用）
- agent-memory core/ 已有六模块不变（T1-T3 是新增模块，不是改既有）

## 四、实施计划

### 第一批（skill 层，半天）

S1-S5 全部零依赖、纯 Markdown/Python 标准库。完成后跑 verify.py 全绿 + 沙箱实测（hook 注入含核心块、search.py 过滤失效条目）。

### 第二批（工具层，随 agent-memory M2）

T1-T3 三个新模块，接口文档 + 自测。T4 衰减/强化等使用数据积累后再做。

### 第三批（论文素材，远期）

双轴记忆模型 + 四层加工管线 + dogfood 实证——论文素材从 M1 起持续积累，与本方案合并。

## 五、风险与克制

- **不过度建层**：单人 agent 记忆库 < 200 条，四层全建可能过重——核心块注入和原子化先做，场景包和衰减看需求
- **防 over-generalization**：核心块不由 agent 在对话中自动改写（Letta 的 self-edit 在单机无评审场景有风险）；由 save/neat 维护
- **防双源漂移**：skill 与 core 的格式契约（四套 schema）是唯一耦合点——变更需两线同步（与 super-memory × agent-memory 的关系一致）
- **防止把注意力从主线引开**：用户当前主线是 super-memory skill 本身的质量与真实使用——本方案是"补全用户轴"的增量，不是新项目
