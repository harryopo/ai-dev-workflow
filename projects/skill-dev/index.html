痛点

为什么需要 Skill？

Agent 不是完全不会做，而是每次都像第一次做。你刚刚纠正过的格式、跑通过的工具顺序，换个任务又要重新解释一遍。

🔄

重复解释

同样是代码审查，明天还要提醒它先看 diff、再看测试、最后列风险。每次换任务就要重新解释一遍。

🤖

不稳定输出

Agent 每次的输出格式、检查步骤、工具使用都不一样。不是不会做，而是没有稳定的执行路径。

📈

经验无法沉淀

你踩过的坑、改过的口径、确认过的边界，如果每次都靠聊天临时补，迟早还会再漏一次。

核心架构

渐进式加载

Agent 并不是一开始就把所有 Skill、所有参考资料都读进来。Skill 采用三层渐进式加载：先用很短的信息判断要不要用，再逐层打开更详细的说明。

三层加载机制

Level 1
元数据 name + description — 会话启动时加载，Agent 据此决定是否触发
~100 tokens
↓ 用户任务匹配 description 时触发
Level 2
SKILL.md 正文 触发条件、工作流程、输出规范、失败处理 — 被调用时全文注入
~2000 tokens
↓ 正文引用 references/ 或 scripts/ 时加载
Level 3
目录资源 references/ scripts/ examples/ — 仅读取当前需要的文件
按需加载

设计原则

Skill 开发的核心原则

这些原则决定了 Skill 的质量上限。违反任何一条，Skill 的效果都会大打折扣。

🎯强模型写，弱模型跑

复杂、模糊、需要归纳经验的部分，交给更强的模型来整理。一旦流程被写成 Skill，后续同类任务就可以由更便宜、更快的模型按步骤执行。验收标准：弱模型也能稳定产出。

🧩渐进式加载

入口短才能准确触发，主干清楚才能稳定执行，资料可追溯才能补细节，动作可执行才能脚本化。不是把所有内容堆在模型面前，而是在每一步只拿当前必要的信息。

📐边界越清楚越好

一个 Skill 做一件事。按任务阶段拆、按输入类型拆、按输出格式拆。可以组合，但不建议都塞进一个 Skill。边界越清楚，后面越好维护。

🐛从特化开始

先覆盖一个具体场景，用真实 case 验证。当同一类规则在 3+ 个不同 case 里重复出现时，再把它泛化。过早泛化会导致误触发率上升。

⚠️失败即素材

不要把失败当作问题，把它当作下一版规则、样例和评测的来源。Gotchas 飞轮：真实失败 → 追加边界 → 下次避免。一个 Skill 越成熟，越清楚哪些路不能走。

🛑不是所有任务都值得 Skill 化

一个边界模糊、很少触发、没人维护的 Skill，不但不会提高效率，反而可能污染路由、浪费上下文。先跑 baseline，再决定要不要写。

目录结构

好 Skill 的最小结构

最小可以只有 SKILL.md，但好用的 Skill 会把触发、执行、资料、验证分开写清楚。

my-skill/
  SKILL.md # 必须
  references/ # 参考资料
  scripts/ # 脚本化动作
  examples/ # 好结果、坏结果
  evals/ # 评测集
SKILL.md
核心说明书。告诉 Agent 什么时候用、按什么顺序做、输出什么格式、什么情况下停下来。包含 frontmatter、触发条件、工作流程、输入规范、输出契约、失败处理、示例。
references/
参考资料，按需加载。长规范、API 文档、业务背景、模板。只有 SKILL.md 引用时才读取，不会一次性塞进上下文。用 ${CLAUDE_SKILL_DIR} 引用。
scripts/
脚本化稳定动作。参数固定 + 每次都执行的动作，做成脚本或 CLI 示例。模型擅长理解意图，但不擅长精确记住参数组合。
examples/
好结果、坏结果、边界样例。让 Agent 能对照判断质量。至少 3 个标准样例、2 个边界样例、1 个反例。
evals/
最小评测集。每次改 Skill 后，用它检查有没有把原本会做的事情改坏。不是证明作者写得对，而是快速发现回归。
能力

Skill Dev 能帮你做什么

从判断任务是否值得 Skill 化，到生成、测试、部署，全流程引导。

前置判断

不是所有任务都值得 Skill 化。先跑 baseline，观察 Agent 是否稳定暴露同一类问题，再决定要不要写。避免创建边界模糊、很少触发的无效 Skill。

baseline 测试 稳定性判断 成本评估
# 前置判断三步法
1. 任务重复出现过几次？
2. Agent 每次稳定犯同一类错？
3. 先跑 3-5 个真实 case

if 不稳定: "边界不清，不适合 Skill 化"

Description 写作

前 250 字符必须包含：做什么 + 触发词 + 产出类型。写之前先回答三个自检问题，改 description 必须同步补正例和反例评测。

三个自检问题 路由触发器 正例/反例
# description 三个自检问题
Q1: 用户真实会怎么提需求？
Q2: 哪些相邻需求不该触发？
Q3: 加载后产出什么类型结果？

# 前 250 字符结构
0-50: 核心功能
50-100: 触发关键词
100-200: 产出类型
200-250: 边界提示

脚本化稳定动作

模型擅长理解意图，但不擅长精确记住参数组合。参数固定 + 每次都执行的动作，做成脚本比让模型每次"想起来"稳定得多。

参数固定 → 脚本化 参数变化 → workflow 偶尔执行 → 写在正文
# 脚本化判断标准
if 参数固定 and 每次执行:
  → 脚本化 (scripts/)
elif 参数变化 and 需要判断:
  → 写进 workflow
else:
  → workflow 里写命令即可
失败处理

四种失败类型与修复动作

每次失败都是改进的素材。识别失败类型，找到对应的修复动作，形成迭代飞轮。

触发错误

该触发没触发 / 不该触发却触发了

description 写得太宽或太窄，和相邻 Skill 触发范围重叠

改 description，补正例和反例评测

步骤遗漏

Agent 跳过关键步骤

workflow 只有原则没有动作，Agent 自由发挥

补 workflow，加检查点，写明确动作

输出不合格

格式错、内容缺、无法验收

输出契约不明确，没有格式模板和示例

补 examples，明确输出契约和模板

工具误用

用错工具或参数组合

Agent 每次"想起来"的参数不一样

补 gotchas，脚本化稳定动作

Gotchas 飞轮

把失败变成边界

不要每次遇到问题就重写整份说明。把真实失败追加成 gotcha：什么情况下不要触发、哪个工具容易误用、连续失败时停在哪里。

G1: 看起来像但不该触发

用户说"帮我看看这段代码"可能是问功能，不是审查。判断依据：是否提到"质量"、"安全"、"性能"等关键词。

G2: 容易误用的工具

不要用 Write 直接覆盖用户文件，先用 Edit 做 diff。Write 会丢失用户未提交的修改。

G3: 连续失败时停止

如果连续 3 次输出不符合格式要求，停下来问用户。不要无限重试。

分工模型

强模型写，弱模型跑

渐进式加载还有一个实际价值：它把"写流程"和"跑流程"分开了。

🧠
写 Skill

强模型（Opus）

  • 归纳经验、提炼流程
  • 处理模糊、复杂的判断
  • 复盘对话，找出纠正点
  • 设计触发条件和边界
→ SKILL.md →
⚙️
跑 Skill

弱模型（Haiku）

  • 按步骤执行流程
  • 遵循明确的约束
  • 输出格式固定的结果
  • 遇到边界知道停下来
评测机制

用 Evals 抓回归

给一组输入，让 Skill 产出结果，再按标准判断好不好。不是为了证明写得对，而是为了快速发现回归。

评测样本结构

类型 数量 用途 示例
核心样本 5-10 个 用户最常提交的任务 标准草稿 → 知识库文章
边界样本 3-5 个 空输入、资料不全、格式混乱 结构混乱的会议纪要
已知坑 3-5 个 之前误触发、乱用工具的案例 不该触发却触发了的场景
// 评测策略
新建 Skill: 比较 "有 Skill" vs "无 Skill"
优化 Skill: 比较 "新版" vs "旧版"

// 每次改 Skill 后用同一把尺子回看
// 才知道是真变好还是看起来更复杂
开发流程

五步开发流程

从需求分析到部署验证，每一步都有明确动作和验收标准。

需求分析

功能定位、触发设计、执行模式、输出规范、参考资料。用对话引导用户明确需求。

生成 SKILL.md

按官方规范生成 frontmatter、触发条件、工作流程、输入规范、输出契约、失败处理。

保存本地

先保存到项目目录，创建完整目录结构。不直接写入全局目录。

本地测试

7 项验收清单 + Evals 评测集。用真实 case 测试，用弱模型验证稳定性。

部署全局

测试通过后复制到 ~/.claude/skills/。先改本地，验证后再部署。

验证

📈 泛化时机

同一条规则在 3+ 个不同 case 里重复出现。用户主动要求"这个也适用另一个场景"。边界条件已经验证清楚。

🏰 特化信号

泛化后误触发率上升。不同场景的输出格式差异太大。用户反馈"什么都能做但什么都做不好"。

🛑 退役条件

模型原生能力已覆盖。维护成本超过收益。流程已过时。和新 Skill 大量重叠。退役不是失败。
