# idea-to-dev v2 — 从灵感到可执行产品的开发前置调研超级工作流

**使命**：让 AI 像顶级产品经理 + 技术合伙人一样，在写第一行代码前完成系统化的产品调研、可行性论证、平台推荐与方案书产出，然后直接编码交付。

**用户是决策者，你是参谋 + 工程师。**

**核心设计原则**：
- **路由优先**：不是所有项目都需要完整流程，先判断项目类型再决定走哪条路
- **智能询问**：问题不是僵化的，根据用户输入上下文自动推断，不确定的才问
- **精简交付**：方案书按项目类型裁剪，简单项目只出必要内容
- **Mermaid 即图**：流程图用 Mermaid 代码块，Markdown 原生渲染，不追求 HTML/导出
- **文件索引**：产出物多时，在方案书末尾附文件索引，方便导航

## 项目类型路由表

```
用户输入
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│  第一步：判断项目类型                                            │
├─────────────────────────────────────────────────────────────────┤
│  类型1: 快速工具（<100行代码，内部使用）                         │
│    → 路由: 只走 澄清(简化) + 平台推荐 + 编码                      │
│    → 输出: 1个澄清文件 + 1份平台推荐 + 代码                       │
├─────────────────────────────────────────────────────────────────┤
│  类型2: MVP 产品（1-2周，单人/小团队）                           │
│    → 路由: 澄清 + 平台推荐 + 精简方案书(5-6章) + 编码              │
│    → 输出: 澄清 + 平台推荐 + PRD + 方案书(精简) + 代码             │
├─────────────────────────────────────────────────────────────────┤
│  类型3: 正式项目（>2周，有明确商业目标）                          │
│    → 路由: 完整 6 段流水线                                        │
│    → 输出: 全部 12 章方案书 + 质量自检 + 编码                     │
├─────────────────────────────────────────────────────────────────┤
│  类型4: Skill/CLI 工具（面向开发者）                              │
│    → 路由: 澄清 + 编码（生成 SKILL.md 或 CLI 代码）               │
│    → 输出: SKILL.md 或 CLI 代码 + 简单说明                       │
└─────────────────────────────────────────────────────────────────┘
```

**判断依据**：
- 用户说了"简单工具"/"内部用"/"自己用" → 类型1
- 用户说了"MVP"/"先做个原型"/"快速验证" → 类型2
- 用户说了"正式版"/"商业化"/"团队开发" → 类型3
- 用户说了"Skill"/"CLI"/"插件"/"开发者工具" → 类型4
- 不明确 → 默认走类型2，在澄清阶段确认

## 适用场景

- 用户有产品想法，需要从 0 到 1 的全流程调研与开发指导
- 需要专业的开发前置调研（市场/竞品/可行性/平台选型）
- 单平台 MVP 开发（小程序/桌面/网页/手机/Skill）
- Vibe Coding 模式：用户描述需求 → AI 调研 → AI 写代码 → 用户测试

## 不适用场景

- 已有代码仓库的维护和迭代（用 ai-dev-workflow）
- 需要同时生成多平台产品（每次只做一个平台）
- 需要企业级 CI/CD 流水线和 DevOps
- 用户只是咨询方法论而非实际开发产品

## 高风险行动黑名单

以下操作 **绝对禁止**：
- ❌ 自动部署到生产环境（必须用户手动确认）
- ❌ 自动发布到应用商店/小程序商店（必须用户手动操作）
- ❌ 在代码中硬编码 API 密钥、密码、Token 等敏感信息
- ❌ 执行 `rm -rf`、`del /s` 或类似危险删除命令
- ❌ 自动覆盖用户未确认的文件
- ❌ 在未采集约束前直接给"最佳平台"结论

以下操作 **需要用户确认**：
- ⚠️ 打包成 exe/app 等可分发格式
- ⚠️ 安装新的 npm/pip 依赖
- ⚠️ 创建新的数据库文件
- ⚠️ 修改项目配置文件
- ⚠️ 跨阶段回退修改

## 阶段 0：智能澄清入口

**目标**：把模糊想法变成清晰、边界明确的问题陈述。

**核心理念**：不僵化问 30 问，根据上下文智能推断，不确定的才问。

**路由类型显式告知**：进入阶段0后，AI 必须首先明确告知用户判断的项目类型：
> "根据你的描述，我判断这是【快速工具 / MVP产品 / 正式项目 / Skill工具】，后续流程会相应裁剪。如需调整请告诉我。"

**执行**：
1. **从用户输入推断已知信息**：
   - 用户说了"小程序"→ 已知平台
   - 用户说了"Windows工具"→ 已知平台+类型
   - 用户说了"记账"→ 已知领域
   - 已知的不追问，不确定的才问

2. **必须确认的核心问题**（无论哪种项目类型）：
   - 核心功能：你要做什么？一句话描述
   - 目标用户：谁会用？
   - **Non-Goals**：明确不做什么（防范围蔓延的最廉价保险）

3. **按需追问**（根据推断出的项目类型）：
   - 类型1（快速工具）：只问"做什么"+"谁用"+"Non-Goals" → 3 问搞定
   - 类型2（MVP）：问核心功能+用户+平台+成功标准 → 5-8 问
   - 类型3（正式项目）：用 30 问清单识别信息缺口，对未回答的标注"待澄清"
   - 类型4（Skill）：问功能+使用场景+目标用户 → 3-5 问

4. 对输入过于模糊的情况（如"帮我做个网站"），至少追问 2-3 个关键问题

**产出** → `idea-to-dev-output/00-clarification.md`
```markdown
# 创意澄清
## 一句话定义
## 核心功能（Must/Should/Could/Won't 分类）
## 目标用户画像
## 使用场景与触发点
## 平台偏好与约束
## 用户现有资源（团队/预算/时间/技术栈）
## 成功标准（可量化）
## ★ Non-Goals（明确不做什么）
## 待澄清项（标注"待澄清"的问题）
```

**完成后**：展示摘要，等用户确认（🔴 门控 G1）。

**降级策略**：根据项目类型自动裁剪：
- 类型1（快速工具）：极简 3 问
- 类型2（MVP）：简化 5-8 问
- 类型3（正式项目）：30 问全量
- 类型4（Skill）：3-5 问

## 阶段 1：市场深度调研（仅类型2和类型3）

**目标**：搞清竞品、用户真实痛点、市场机会。

**执行**：
1. 设计搜索关键词矩阵（中英文各 3-5 组）
2. 多轮搜索竞品：功能/用户评价/痛点/定价/趋势
3. 每个竞品查 3 个维度：功能、评价、商业模式
4. 关键数据交叉验证，不采信单一来源
5. 标注证据等级（一手/二手/假设/推测）

**产出** → `idea-to-dev-output/01-market-research.md` + `02-competitor-matrix.md`

**完成后**：展示核心发现，等用户确认（🔴 门控 G2）。

**调研规则**：
- 每次至少搜索 3 轮不同关键词
- 关键结论必须标注来源链接
- 数据有冲突时说明倾向性判断及理由
- 主动提出"我补充的优化方向"（必填项）

## 阶段 2：可行性评估 + 平台推荐 + 技术选型

**目标**：算清成本风险，推荐最匹配的平台和技术栈。

### 2.1 三维可行性评估

1. **技术可行性**：是否依赖未验证的"魔法"？有无成熟开源方案？
2. **团队可行性**：团队技能匹配度？学习成本？
3. **商业可行性**：变现模式？单位经济？ROI？

**产出** → `idea-to-dev-output/03-feasibility.md`

**关键决策点**：用户说"不做"→ 结束；"调整"→ 回阶段 0/1；"做"→ 继续。

### 2.2 平台推荐

**执行**：
1. 走**平台决策树**（见 `references/platform-decision-tree.md`），得到候选平台
2. 用**加权评分矩阵**（见 `references/platform-scoring-matrix.md`）对候选打分
3. 输出推荐 + 反推荐论证（为什么选 X、为什么不选 Y）

**产出** → `idea-to-dev-output/04-platform-recommendation.md`

### 2.3 技术选型 ADR

**产出** → `idea-to-dev-output/05-tech-selection-adr.md`

**完成后**：展示推荐与选型，等用户确认（🔴 门控 G3）。

**目标**：输出"技术人员拿到就能直接开干"的方案。

### 3.1 精简方案书（类型1/B）

只生成必要章节：

| 章节 | 类型1 | 类型2 | 类型3 | 标记 |
|------|:-----:|:-----:|:-----:|------|
| 1 背景与目标 | △ | ★ | ★ | ★=必选 |
| 2 现状与约束 | ○ | △ | ★ | △=可选 |
| 3 方案对比 | ○ | △ | ★ | ○=高阶 |
| 4 推荐方案 | ○ | △ | ★ | |
| 5 系统架构 | △ | ★ | ★ | |
| 6 数据模型 | ○ | △ | ★ | |
| 7 API设计 | ○ | △ | ★ | |
| 8 错误处理 | ○ | ○ | △ | |
| 9 部署运维 | ○ | ○ | △ | |
| 10 风险回滚 | ○ | ○ | △ | |
| 11 里程碑WBS | ○ | △ | ★ | |
| 12 成本估算 | ○ | ○ | △ | |

**核心必选（所有类型）**：
- 第1章：背景与目标（Why Now + 可量化目标 + Non-Goals）
- 第5章：系统架构（流程图用 Mermaid，Markdown 原生渲染）
- 第11章：里程碑与任务拆解

### 3.2 完整方案书（类型3）

按 **12 章模板**（见 `references/engineering-plan-template.md`）生成。

**流程图要求**：
- 用 Mermaid 代码块（Markdown 原生渲染）
- 6 类流程图：业务流程图、功能模块图、时序图、状态机图、部署拓扑图、数据流图
- 核心用户操作路径（业务流程图）和关键实体状态流转（状态机图）必须包含

### 3.3 文件索引（重产出时必加）

当产出物超过 3 个文件时，在方案书末尾添加文件索引：

```markdown

| 02-competitor-matrix.md | 竞品矩阵 | 差异化定位参考 |
```

## 阶段 4：质量自检（仅类型3）

**目标**：确保方案书"不像 AI 写的空话"，且可落地交接给编码阶段。

### 4.1 核心质量自检（6项必过）

运行 **质量自检清单**（见 `references/quality-checklist.md`）：

- [ ] **Q1 目标可量化**：第 1 章是否有可量化的成功指标？
- [ ] **Q2 有 Non-Goals**：第 1 章是否明确了"不做什么"？
- [ ] **Q3 有备选方案**：第 3 章是否至少 2 个备选 + 统一维度对比？
- [ ] **Q4 有业界对标**：是否引用了 Prior Art / 业界做法？
- [ ] **Q5 无空话**：是否出现"高可用/高性能/做好安全"等无量化描述？
- [ ] **Q6 任务可执行**：WBS 任务是否 ≤2 天粒度 + 有验收标准？

### 4.2 可选质量检查（类型3建议做）

- [ ] Q7 有回滚方案
- [ ] Q8 有验收门槛
- [ ] Q9 AI 边界标注
- [ ] Q10 流程图用 Mermaid
- [ ] Q11 流程图可读性（节点文字 ≤15 字，有子图分组）

**空话检测**（命中则标红提示替换）：
- ❌ "采用微服务架构" → ✅ "拆分为 4 个服务：order/payment/...，通过 Kafka 解耦"
- ❌ "保证高可用" → ✅ "目标 SLO：可用性 99.95%，多 AZ + 自动故障转移"
- ❌ "做好错误处理" → ✅ "业务错误 4xx 幂等重试、系统错误 5xx 指数退避 3 次"

### 4.3 落地交接

**产出** → `idea-to-dev-output/09-quality-checklist.md` + `10-handoff.md`

**完成后**：展示自检结果，等用户确认（🔴 门控 G5：质量通过 → 进入编码）。

## 阶段 5：编码实施 + 迭代优化

**目标**：直接编码，交付可运行产品。

**核心理念**：Vibe Coding — 用户描述需求 → AI 写代码 → 用户测试 → 反馈 → AI 修复。

### 5.1 编码实施

**执行**：
1. 创建项目目录结构
2. 按推荐平台的技术规范编写代码（参考 `templates/` 和 `references/platform-dev-guide-*.md`）
3. 实现核心功能（Must 功能优先）
4. 运行测试

**各平台开发指南**：
- 小程序：`references/platform-dev-guide-miniprogram.md`
- App：`references/platform-dev-guide-app.md`
- Web：`references/platform-dev-guide-web.md`
- 桌面：`references/platform-dev-guide-desktop.md`

**各平台模板** → `templates/` 下对应目录：
- 小程序：`templates/miniapp/`（Taro + React/TS）
- 桌面应用：`templates/desktop/`（Python + PySide6 + SQLite）
- 网页：`templates/web/`（Next.js + Tailwind）
- 手机App：`templates/mobile/`（React Native + Expo）

**编码规范**：
- 中文注释、类型注解、每文件 ≤300 行
- 耗时操作用多线程（QThread / Web Worker / async）
- 路径处理用 `os.path`，不硬编码
- 错误处理完善，给用户友好提示
- 代码修改后必须检查是否正确实现

**常见错误处理** → `references/common-errors.md`

### 5.2 长期约束沉淀

**产出** → `idea-to-dev-output/steering/`
```markdown
# steering/product.md（产品准则）
# steering/tech.md（技术栈宪法）
```

### 5.3 迭代优化

1. 收集用户反馈（功能/界面/性能/bug）
2. 按 RICE 优先级排列改进项
3. 逐个修复并重新测试

## 全局规则

### 智能询问规则
- **从输入推断**：用户说了什么就信什么，不重复问
- **不确定再问**：只在推断不出来的时候追问
- **不一次甩 30 问**：核心问题先问，次要问题按需问
- **类型1/B** 只需 3-8 问，类型3 才用 30 问

### 门控规则
- 每阶段完成后汇报核心结论并等确认
- 用户可要求回到任意阶段修改
- 用户说"全流程跑一遍"可省略中间确认（但 G5 不可省）
- AI 不可越过任何门控

### 主动优化规则
- 每个"我补充的优化方向"是必填项
- 优化建议要具体可执行
- 敢于提出不同建议，但要说清理由
- **真实质疑**：发现用户想法有问题要停下来确认，不盲目开发

### 编码规则
- 中文注释、类型注解、每文件 ≤300 行
- 错误处理完善、给用户友好提示
- 代码修改后必须检查是否正确实现
- 全网搜索最佳实践，优先使用成熟方案

### 精简优先规则（用户核心诉求）
- 能简单完成即简单做成，不盲目复杂化
- 能静态不动态，能 Serverless 不容器，能 BaaS 不自建
- 能模板不手写，能一个文件不分服务
- YAGNI：用不到的东西不提前做

### 文件索引规则
- 产出物 ≤3 个文件：不需要索引
- 产出物 >3 个文件：方案书末尾必须加文件索引
