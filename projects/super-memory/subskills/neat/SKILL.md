# Neat — 洁癖级知识同步

> `super-memory` 的 neat 子命令。里程碑时对项目文档与记忆做审查、合并、修正、精简。
> 本文件由父级用 Read 加载，不是独立 skill；工具授权看父级 frontmatter。

你是**知识库编辑**，不是记录员。记录员只会往后追加；编辑会审查全局、合并重复、修正过期、隔离废弃、精简膨胀。

知识分三层，受众不同、职责不重叠，**三层都要写**：agent 记忆库（自己跨会话用）、项目根规则文件（当前项目里的 AI 用）、`docs/` + `README.md`（别人用）。规则文件里写"新增了 5 个路由" ≠ docs 里"下游怎么接这 5 个路由"——只写一层就是漏。完整版表格与代价见 `../../references/knowledge-layers.md`。

规则文件是**规则手册，不是变更日志**。判断一条信息该不该进规则文件，只问一句：**下次 AI 写代码时如果没看到这条，会不会犯错？** 会 → 进；只是"上次会话发生了什么" → 那是叙事，归宿是 git log / CHANGELOG，不是规则文件顶部。✅/❌ 对照表见 `../../references/knowledge-layers.md`。

## 什么时候不该走 neat

| 场景 | 为什么 | 该做什么 |
|---|---|---|
| "整理一下这段代码 / 这个函数" | 对象是代码，不是知识库 | 直接重构 |
| 只改了一个 typo、一行配置 | 没有跨层事实变化 | 改完就提交，别起审查 |
| 别人正在改同一批文档（mtime 比本次会话新） | 那是别人的在制品 | 标「未处理」，不动它 |
| 只想给下次会话留个交接说明 | 是 handoff，不是全库审查 | 走 save |

## 第零步：尺寸体检（最高优先级）

任何同步动作之前先量尺寸：

| 文件 | 软上限 | 超了怎么办 |
|---|---|---|
| 规则文件（`CLAUDE.md`/`AGENTS.md`） | ~300 行 / ~15KB | 扫顶部叙事段 → 隔离或迁 docs；概览只留 1–3 行 + 速查表 |
| 记忆索引 `MEMORY.md` | ~150 行 | 删被新版取代的、单次事故复盘、可用代码代替的机制说明 |
| 单条 memory 文件 | ~100 行 | 通常在塞多件事 → 拆开或隔离 |
| `docs/<single>.md` | ~1500 行 | 切多文件 + 目录索引 |

**超尺寸优先于补漏**：挤满叙事的规则文件让下次 AI 看不见真正重要的规则，补也白补。**先精简（心态：什么不该在这）→ 再补本次增量（心态：什么该补到这）**，不可合并做。

## 第一步：盘点（机械枚举，不许跳）

先 `ls` 再判断。

1. 按 `../../references/memory-addressing.md` 定记忆位（规则文件 → 探测 → 兜底），**列出并读**记忆索引与被引条目。目录不存在时先分辨是"这宿主没有"还是"寻址没做对"。同时盘点 `.ai/`：`HANDOFF.md` 与 `knowledge/` 都在范围内，但**交接记录的历史版本条目只追加不改写**，长期库条目只做置信度降级。
2. 对本次涉及的每个项目：`ls <root>/` → `ls <root>/docs/`（缺失也要确认）→ `find <root> -maxdepth 2 -name "*.md" -not -path "*/node_modules/*" -not -path "*/.git/*"` 兜底 → 读 `README.md`、规则文件、每个 `docs/*.md`
3. 读宿主的全局配置（若有）
4. 回顾本次会话全部内容
5. `ls .learnings/` + 扫待处理项

输出内部文件清单，每项标「评估过 / 要改 / 不用改」。**漏一项不行**，这是最容易翻车的地方。

## 第二步：识别变更（变更影响矩阵）

不只看"多了什么新事实"，要看它**波及哪些文档层**。逐类矩阵（API / 环境变量 / 数据表 / 大特性 / 跨项目）见 `../../references/change-impact.md`。

两条最常漏：**跨项目**——改了 A 且 B 依赖 A，B 的 docs 也要改；**记忆层**——相对时间→绝对日期、过期→改掉、重复→合并、已完成待办→隔离。

## 第 2.5 步：删除审查（涉及删除时强制）

凡是要删文件、删目录、删记忆条目，先走完这一步，用户确认后才动。删除不可逆，宁可多确认一次。

1. 对目标目录做全局枚举，把每项分四类：**确认删除 / 待确认删除 / 需迁移合并 / 确认保留**
2. grep 检查每项是否被引用
3. 按 `../../references/delete-review-template.md` 生成审查报告，落到 `.tmp/neat-delete-review-<时间>.md`
4. 用 AskUserQuestion 确认（四选项：全确认 / 部分确认 / 全部取消 / 重新审查）
5. 确认后按该文件的执行规范操作：**一律 `mv` 到 `.tmp/neat-quarantine/<日期>/` 保留原相对路径，不 `rm`**；随后清理引用与索引行

## 第三步：实际修改（用工具，不只是描述）

必须真的用 Edit 改现有文件、用 Write 建新文件、用隔离处理废弃。"我会怎么改"不算完成。

**顺序**：先改 `docs/`（改错影响外部）→ 再改规则文件 → 最后理记忆。先动外部优先级最高的。

编辑原则：

- **减优于加（最重要）**：单次同步后规则文件净涨幅 > 30 行是红灯，多半在写叙事。后者回去删或迁 docs。
- **合并优于追加**：新信息是旧信息的更新 → 改旧条目；加新条目前先 grep 同关键字，看能不能并进去。
- **隔离优于保留**：已完成的临时计划、被推翻的决策、已被取代的项目记忆、单次事故流水账 → 走第 2.5 步隔离。
- **精确优于冗长**：一条记忆说一件事。
- **受众不混、指针不重复**：规则文件不抄 docs 全文，docs 不写"我记得上次……"；docs 已详写的事实，规则文件只在指针表出现一次。

## 第四步：自检清单（逐项过，打不了勾就回去补）

尺寸/反膨胀（先查这组，不达标回头精简）：

- [ ] 规则文件净涨幅 ≤ 30 行
- [ ] 没新增"X 起 Y 上线，详见 docs/Z.md"式叙事
- [ ] 没在规则文件里抄 docs 的详细机制
- [ ] 单条 memory 没超 ~100 行

完整性/反漏改：

- [ ] 第一步列出的每个文件都判过"不用改"或"已改"
- [ ] 索引里每个链接指向存在的文件；每条 description 与正文对得上
- [ ] 记忆之间无矛盾；无法自动判断的矛盾列进「未处理」让用户定
- [ ] 规则文件提到的路径/命令/工具/环境变量在代码里真实存在（`ls`/`grep` 确认过）
- [ ] README 的安装运行步骤与代码一致
- [ ] 新增 API 路由 / 环境变量 / 数据库表：**矩阵里指定的两处都出现过**（对照 `../../references/change-impact.md`，不是只改一处）
- [ ] 跨项目下游 docs 跟着改了
- [ ] 相对时间清零：`grep -rE "今天|昨天|刚刚|最近|上周|today|yesterday|recently" <范围>`
- [ ] `.learnings/` 待处理项已扫过：该归档的走 save，该升档的走 handoff/promote；扫到 0 条要写清"确实没有"还是"格式没对上"
- [ ] `.ai/HANDOFF.md` 必需节齐、历史版本记录未被改写、`[V]` 条目已过代码核验

每条命中数都要贴实测输出。"扫过、没问题"不算。

## 第五步：变更摘要

按 `../../references/change-summary.md` 的模板，在**所有修改完成后**给用户摘要。

## 特殊情况

- **没有 README 或规则文件**：已到"有可运行代码"阶段 → 建；还在 vibe 阶段 → 跳过并在摘要说明。
- **本次会话没产生新事实**：仍要审查现有记忆与文档的过期/冲突/相对时间——审查本身就有价值。
- **发现以前同步漏了**：修掉。你是这个项目的持续编辑，历史漏洞归你管。
- **同目录有别人的在制品**：先比 mtime，比上次测量更新的产物可能是另一个会话正在写的 → 标「未处理」，不改它、不删它、不为让它变绿而动它的断言。
- **与兄弟命令衔接**：`Recurrence-Count` ≥ 3 → 提示 promote；capture 记了但未归档 → 提示 save；精简出的精华 → 进 promote。
