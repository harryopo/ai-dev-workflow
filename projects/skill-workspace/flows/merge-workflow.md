# Skill 合并工作流

## 概述

合并 skill 是将多个相关 skill 整合为一个更强大、更完整 skill 的过程。

### 合并目标

1. **消除冗余** — 减少功能重叠，降低维护成本
2. **增强能力** — 集成多个 skill 的优点，形成更强功能
3. **优化体验** — 统一触发条件和输出规范，减少用户困惑
4. **解决问题** — 修复原 skill 的痛点和缺陷

### 合并意义

- **对用户** — 一个 skill 解决多种需求，减少选择成本
- **对维护** — 统一维护入口，降低维护复杂度
- **对质量** — 集成最佳实践，提升整体质量

## 合并流程

### 第一步：深度分析原 Skill

**目标** — 全面深入理解每个原 skill 的设计理念、核心功能和优化空间

**产物** — 深度分析报告（v5.1 新增）
- 保存到：`./artifacts/analysis/deep-analysis-{date}-{skill-names}.md`
- 包含：功能清单、架构设计、提示词质量、子技能调用工程、优化空间

**操作** — 阅读每个 skill 的 SKILL.md，重点关注：

#### 1.1 功能清单分析

- **核心功能** — skill 的主要功能是什么
- **辅助功能** — 支持核心功能的辅助功能
- **边界功能** — 不应该触发的场景
- **缺失功能** — 用户可能需要但缺失的功能

#### 1.2 架构设计分析

- **触发条件** — 什么时候被激活
- **工作流程** — 具体执行步骤和分支逻辑
- **输出规范** — 期望的输出格式和质量标准
- **子技能** — 依赖的子技能和调用方式
- **参考资料** — 引用的 references 文件

#### 1.3 提示词质量分析

- **触发词精准度** — 是否精准匹配用户意图
- **指令明确性** — 是否清晰描述了执行步骤
- **输出格式规范** — 是否明确了输出格式
- **边界条件说明** — 是否说明了不适用场景
- **示例完整性** — 是否有正例、反例、边界示例

#### 1.4 子技能调用工程分析

- **调用方式** — 如何调用子技能（Skill tool / Read）
- **参数传递** — 如何传递参数给子技能
- **结果整合** — 如何整合子技能的结果
- **错误处理** — 子技能失败时如何处理
- **降级策略** — 子技能不可用时的降级方案

#### 1.5 优化空间分析

- **性能优化** — 是否有性能瓶颈
- **准确性优化** — 是否有误触发或漏触发
- **易用性优化** — 是否有使用门槛
- **可维护性优化** — 是否易于维护和扩展
- **可扩展性优化** — 是否易于添加新功能

### 第二步：审查原 skill

**目标** — 了解原 skill 的质量现状

**操作** — 调用 review 子技能，对每个原 skill 进行 Darwin 9 维度评分：

1. **结构完整性** — frontmatter、目录结构、references
2. **指令具体性** — 触发条件、工作流程、输出格式
3. **失败模式编码** — 错误处理、边界条件、降级策略
4. **可执行具体性** — 命令可执行、路径可访问、依赖可安装
5. **边界条件** — 输入验证、异常处理、超时控制
6. **用户确认点** — 关键决策点、用户交互、确认机制
7. **高风险行动黑名单** — 危险操作拦截、安全审查、权限控制
8. **实测表现** — evals 评测集、实测数据、效果指标
9. **反例黑名单检查** — 反例完整性、误用防护、常见问题

**输出** — 每个 skill 的审查报告（评分 + 优缺点 + 改进建议）

### 第三步：理解原 skill

**目标** — 深入理解每个 skill 的设计意图

**操作** — 基于第一步的深度分析，重点关注：

- **核心价值** — 这个 skill 解决什么问题
- **用户场景** — 什么用户在什么场景下使用
- **使用频率** — 用户多久使用一次
- **依赖关系** — 依赖哪些其他 skill 或工具
- **Gotchas** — 已知的坑和注意事项

**输出** — 每个 skill 的理解摘要

---

### 第四步：询问用户

**目标** — 明确合并方向和用户需求

**询问内容**：

1. **保留优点** — 哪些功能/特性必须保留？
2. **解决痛点** — 哪些问题必须解决？
3. **新需求** — 有没有需要新增的功能？
4. **优先级** — 哪些功能最重要？
5. **约束条件** — 有没有特殊限制？
6. **使用场景** — 典型的使用场景是什么？
7. **用户群体** — 目标用户是谁？
8. **成功标准** — 什么情况下认为合并成功？

**输出** — 用户需求清单（优先级排序）

---

### 第五步：网上调研

**目标** — 搜索最佳实践和解决方案

**产物** — 调研报告（v5.1 新增）
- 保存到：`./artifacts/research/research-report-{date}-{topic}.md`
- 包含：解决方案、最佳实践、踩坑经验、竞品分析、用户反馈

**搜索内容**：

1. **解决方案** — 针对痛点的现有方案
2. **最佳实践** — 行业推荐做法
3. **踩坑经验** — 他人遇到的问题
4. **开源项目** — 可参考的实现
5. **竞品分析** — 类似 skill 的对比分析
6. **用户反馈** — 社区对类似 skill 的评价

**搜索策略**：

- 使用 multi-search-engine 进行多引擎搜索
- 搜索 GitHub 上的类似项目
- 搜索技术博客和论坛
- 使用 deep-research-pro 进行深度调研

**输出** — 调研报告（方案 + 经验 + 参考 + 竞品分析）

---

### 第六步：综合优化

**目标** — 设计合并方案

**产物** — 合并方案（v5.1 新增）
- 保存到：`./artifacts/merge/merge-proposal-{date}-{skill-names}.md`
- 包含：背景、深度分析结果、审查结果、用户需求、调研结果、合并方案、开发计划

**优化原则**：

1. **保留优点** — 原 skill 的优秀设计必须保留
2. **解决痛点** — 原 skill 的问题必须修复
3. **集成新功能** — 用户需求和调研结果要融入
4. **简化结构** — 减少不必要的复杂度
5. **统一规范** — 触发条件和输出格式统一
6. **优化提示词** — 提升触发精准度和指令明确性
7. **优化子技能调用** — 提升调用效率和错误处理
8. **优化用户体验** — 降低使用门槛，提升易用性

**输出** — 合并方案文档（详见输出格式）

---

### 第七步：正常工作流

**目标** — 按标准流程开发合并后的 skill

**流程**：

1. **分阶段开发** — 按方案逐步实现
2. **循环审查** — 每阶段完成后审查
3. **用户确认** — 每阶段完成后确认
4. **本地交付** — 最终交付完整 skill

**输出** — 合并完成的 skill

## 用户确认流程

### 确认时机

每个阶段完成后都需要用户确认：

1. **分析完成后** — 确认分析结果是否准确
2. **审查完成后** — 确认审查结果是否准确
3. **理解完成后** — 确认理解是否正确
4. **需求收集后** — 确认需求是否完整
5. **调研完成后** — 确认调研结果是否可用
6. **方案设计后** — 确认合并方案是否满意
7. **开发完成后** — 确认最终成果是否符合预期

### 确认方式

```markdown
## ✅ 阶段确认

**当前阶段：** [阶段名称]

**已完成：**
- [已完成内容 1]
- [已完成内容 2]

**产出：**
- [产出物 1]
- [产出物 2]

**请确认：**
1. [ ] 分析结果准确
2. [ ] 产出物符合预期
3. [ ] 可以进入下一阶段

**反馈：**
[用户填写反馈]
```

### 处理反馈

- **确认通过** — 进入下一阶段
- **需要修改** — 根据反馈修改后重新确认
- **方向调整** — 回到第三步重新收集需求

## Gotchas

### G1: 合并不是简单拼接
- 合并不是把多个 skill 的内容复制到一起
- 需要重新设计工作流程，消除冗余
- 需要优化提示词，提升触发精准度
- 需要优化子技能调用，提升效率

### G2: 保留优点比解决缺点更重要
- 用户已经习惯的优点不能丢
- 新方案必须兼容原有使用习惯
- 提示词优化不能破坏原有触发逻辑

### G3: 用户确认是必要环节
- 每个阶段都要用户确认
- 不要假设用户的意图
- 深入调研用户需求，不要只问表面问题

### G4: 调研要充分
- 不要闭门造车
- 搜索最佳实践和踩坑经验
- 分析竞品，找到差异化优势
- 了解用户反馈，找到真实需求

### G5: 测试要覆盖
- 合并后的 skill 必须有完整的 evals
- 确保功能不退化
- 确保提示词优化有效
- 确保子技能调用正常

### G6: 提示词优化要谨慎
- 提示词优化可能影响触发逻辑
- 优化后必须重新测试触发精准度
- 优化后必须重新测试输出质量
- 优化后必须重新测试边界条件

### G7: 子技能调用工程要完善
- 子技能调用方式要统一
- 参数传递格式要规范
- 结果整合逻辑要清晰
- 错误处理机制要完善
- 降级策略要明确
