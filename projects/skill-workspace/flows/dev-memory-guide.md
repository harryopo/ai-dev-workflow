# 开发记忆与发布清洗机制指南

> **版本：** v1.0（随 skill-workspace v5.3.0 引入）
> **目的：** 规范 Skill 开发/优化过程中的记忆沉淀，防止开发记忆污染主 SKILL.md，确保发布产物纯净。

---

## 一、背景与动机

### 1.1 问题场景

在 Skill 迭代过程中，常见以下"污染"现象：

| 污染类型 | 表现 | 危害 |
|----------|------|------|
| **更新概要污染** | SKILL.md 末尾追加"v5.2 新增 xxx"等变更日志 | 主文档膨胀，消耗调用 token，干扰 LLM 读取 |
| **版本说明污染** | SKILL.md 开头加入"本版本相比上一版本的改进" | LLM 误将这些说明当作指令执行 |
| **开发笔记污染** | SKILL.md 中夹杂 TODO、踩坑记录、临时注释 | 上传开源时暴露内部开发过程 |
| **决策记录污染** | SKILL.md 中记录"为什么选择 A 而非 B" | 他人调用时被无关决策历史干扰 |

### 1.2 设计目标

1. **开发期可追溯** — 改动有据可查，方便回滚和复盘
2. **发布期可清洗** — 一键清除开发痕迹，产出纯净发布包
3. **主文档零污染** — SKILL.md 只包含 Skill 指令，不包含任何开发记忆
4. **自动化触发** — 关键词识别，自动提醒清洗

## 二、记忆文件规范

### 2.1 文件命名与位置

```
{skill-name}/
├── SKILL.md              # 主文档（纯净，不含开发记忆）
├── .dev-memory.md        # 开发记忆文件（开发期使用，发布前清洗）
├── references/
│   └── ...
└── ...
```

**命名规则：**
- 文件名：`.dev-memory.md`
- 使用 `.` 前缀，标识为"隐藏文件/开发期文件"
- 与 SKILL.md 同级，便于查找
- 不放入 references/（避免被 LLM 按需加载）
- 不放入 artifacts/（避免与正式产物混淆）

### 2.2 文件结构

```markdown
# 开发记忆文件 — {skill-name}

> **⚠️ 本文件为开发记忆，不属于 Skill 主体内容，不会随 Skill 发布。**
>
> **用途：** 记录 Skill 开发/优化过程中的改进概要、决策记录、踩坑经验、待办事项等。
>
> **清洗时机：** 当用户说"正式部署"、"开源"、"发布到社区"等关键词时，
> 必须先执行清洗流程，再执行部署。
```

## 三、清洗流程

### 3.1 清洗触发条件

**自动触发（LLM 识别关键词）：**

当用户在对话中提到以下关键词时，LLM 必须主动询问是否执行清洗：

| 类别 | 触发词 |
|------|--------|
| **部署类** | "正式部署"、"部署到全局"、"部署到生产"、"部署到线上" |
| **开源类** | "开源"、"发布到 GitHub"、"上传到社区"、"公开" |
| **发布类** | "打包发布"、"发布新版本"、"release"、"publish" |
| **分享类** | "分享给他人"、"给别人用"、"团队共享" |

**手动触发：**

用户主动说"清洗"、"清理开发记忆"、"准备发布"等。

**流程触发：**

在以下流程中自动检查：
- 流程五：部署（部署前必须检查）
- 流程七：合并（合并产物发布前必须检查）

### 3.2 清洗步骤

```
第一步：检测 .dev-memory.md 是否存在
  ↓ 存在
第二步：提示用户
  "检测到开发记忆文件 .dev-memory.md，发布前需要清洗。
   选择：
   A. 清洗后发布（推荐）— 清除主文档中的开发记忆痕迹，保留 .dev-memory.md 在本地
   B. 直接发布（不推荐）— 可能泄露开发过程
   C. 取消发布，先查看 .dev-memory.md 内容"
  ↓ 用户选择 A
第三步：扫描主文档污染
  ├── 扫描 SKILL.md
  │   ├── 检查是否包含"更新概要"、"变更日志"、"版本说明"
  │   ├── 检查是否包含 "vX.Y 新增"、"vX.Y 修改" 等版本标记
  │   ├── 检查是否包含 TODO、FIXME、HACK 等开发注释
  │   ├── 检查是否包含"为什么选择 X" 等决策记录
  │   └── 检查是否包含临时性、开发期特有的指令
  ├── 扫描 subskills/*/SKILL.md（同上）
  └── 扫描 references/*.md（同上）
  ↓ 发现污染
第四步：清除污染
  ├── 备份原文件（可选，询问用户）
  ├── 从主文档中移除开发记忆内容
  ├── 保留功能指令、工作流程、参考资料等正式内容
  └── 将移除的内容归档到 .dev-memory.md
  ↓
第五步：验证清洗结果
  ├── 主文档只包含 Skill 指令
  ├── 无版本标记、无开发注释、无决策记录
  └── 功能完整性未受影响（跑一遍 evals）
  ↓
第六步：生成清洗报告
  → 保存到 ./artifacts/cleanup/cleanup-report-{date}-{skill-name}.md
  ↓
第七步：执行发布/部署
```

## 四、LLM 调用时的记忆沉淀流程

### 4.1 何时触发记忆沉淀

当 skill-workspace（或 dev 子技能）执行以下操作后，必须触发记忆沉淀：

1. **优化 Skill 后**（流程四完成）
2. **合并 Skill 后**（流程七完成）
3. **MCP 整合后**（流程八完成）
4. **修复 bug 后**
5. **调整触发词后**
6. **审查发现新问题并解决后**

### 4.2 沉淀流程

```
第一步：识别变更
  ├── 识别本次操作改了什么
  ├── 识别改前和改后的状态
  └── 识别验证结果
  ↓
第二步：生成记忆记录
  ├── 按 .dev-memory.md 的格式生成记录
  ├── 包含 What/Why/Before/After/Verification
  └── 包含版本号和时间戳
  ↓
第三步：追加到 .dev-memory.md
  ├── 如果 .dev-memory.md 不存在，创建文件
  ├── 如果存在，追加到"记忆记录区"
  └── 不要覆盖已有记忆
  ↓
第四步：确认主文档未被污染
  ├── 检查 SKILL.md 是否包含开发记忆
  ├── 如果包含，移除并迁移到 .dev-memory.md
  └── 确保主文档纯净
```

### 4.3 沉淀示例

**场景：优化了 description 的触发词**

```markdown
### v5.3.1 — 2026-08-01

#### 改进概要

**修改：description 触发词优化**

- **What:** 将 "skill开发" 触发词扩展为 "skill开发、创建skill、新建skill、写个skill、帮我做个skill"
- **Why:** 用户反馈原触发词太窄，"写个skill" 等常见表达无法触发
- **Before:** description 只包含 "skill开发" 一个触发词
- **After:** description 包含 5 个触发词，覆盖用户常见表达
- **Verification:**
  - [x] evals 测试通过率从 75% 提升到 95%
  - [x] 误触发率未上升
  - [x] 边界样例全部通过
```

## 五、反模式

### 5.1 禁止的行为

| 反模式 | 表现 | 正确做法 |
|--------|------|----------|
| **主文档写更新日志** | SKILL.md 末尾追加 "## 更新历史" | 写入 .dev-memory.md |
| **主文档写决策记录** | SKILL.md 中记录 "为什么选择 A" | 写入 .dev-memory.md |
| **主文档写 TODO** | SKILL.md 中包含 "- [ ] 待办" | 写入 .dev-memory.md |
| **主文档写开发注释** | SKILL.md 中包含 "<!-- TODO: 优化这里 -->" | 写入 .dev-memory.md |
| **版本标记污染** | SKILL.md 中标注 "(v5.2 新增)" | 移除版本标记，写入 .dev-memory.md |
| **不清洗就发布** | 直接部署包含开发记忆的 Skill | 先清洗，再部署 |
| **清洗后丢失记忆** | 清洗时直接删除 .dev-memory.md | 清洗只清除主文档污染，保留 .dev-memory.md |

### 5.2 边界情况

**Q: references/ 中的正式参考文档可以包含版本信息吗？**

A: 可以，但只能是"该参考文档自身的版本信息"，不能是"Skill 的开发记忆"。
- ✅ `references/darwin-rubric.md` 中标注 "基于 SkillLens 论文 v2.0"
- ❌ `references/darwin-rubric.md` 中记录 "v5.2 新增 D10 维度"

**Q: README.md 可以包含版本历史吗？**

A: 可以。README.md 是面向用户的说明文档，不进入 LLM 上下文，可以包含正式的版本历史。
- ✅ README.md 中包含 "## 版本历史" 章节
- ❌ SKILL.md 中包含 "## 版本历史" 章节

**Q: 子技能的 SKILL.md 可以包含开发记忆吗？**

A: 不可以。subskills/*/SKILL.md 与主 SKILL.md 同级，是 Skill 主体的一部分，同样不能包含开发记忆。

## 七、自动化支持

### 7.1 LLM 自动识别

当 LLM 识别到用户提到清洗触发词时，应主动执行以下流程：

```
用户说："帮我部署到全局"
  ↓
LLM 识别：包含"部署到全局" → 触发清洗检查
  ↓
LLM 检查：.dev-memory.md 是否存在？
  ├── 存在 → 询问用户是否清洗
  └── 不存在 → 跳过清洗，直接部署
  ↓
用户选择清洗 → 执行清洗流程（第三节）
  ↓
清洗完成 → 生成清洗报告
  ↓
继续执行部署流程（流程五）
```

### 7.2 清洗脚本（可选）

对于大型 Skill，可以编写清洗脚本自动化处理：

```python
#!/usr/bin/env python3
"""
Skill 清洗脚本 — 清除主文档中的开发记忆痕迹
用法：python scripts/cleanup.py [skill-dir]
"""
import re
import sys
from pathlib import Path

# 污染模式
PATTERNS = [
    # 更新概要
    (r'##\s*(更新历史|变更日志|版本说明|更新概要).*?(?=\n##\s|\Z)', '更新概要'),
    # 版本标记
    (r'\(v\d+\.\d+.*?新增\)', '版本标记'),
    (r'\(v\d+\.\d+.*?修改\)', '版本标记'),
    # 开发注释
    (r'<!--\s*TODO:.*?-->', '开发注释'),
    (r'<!--\s*FIXME:.*?-->', '开发注释'),
    # 决策记录
    (r'##\s*决策记录.*?(?=\n##\s|\Z)', '决策记录'),
]

def cleanup_skill_md(file_path: Path) -> list:
    """清洗 SKILL.md 文件，返回清除的内容"""
    content = file_path.read_text(encoding='utf-8')
    removed = []
    for pattern, ptype in PATTERNS:
        matches = re.finditer(pattern, content, re.DOTALL)
        for match in matches:
            removed.append({
                'type': ptype,
                'content': match.group(),
                'line': content[:match.start()].count('\n') + 1
            })
            content = content.replace(match.group(), '')
    file_path.write_text(content, encoding='utf-8')
    return removed

def main():
    skill_dir = Path(sys.argv[1] if len(sys.argv) > 1 else '.')
    # 清洗主 SKILL.md
    skill_md = skill_dir / 'SKILL.md'
    if skill_md.exists():
        removed = cleanup_skill_md(skill_md)
        print(f'清洗 {skill_md}: 移除 {len(removed)} 处污染')
    # 清洗子技能
    for sub_skill_md in (skill_dir / 'subskills').rglob('SKILL.md'):
        removed = cleanup_skill_md(sub_skill_md)
        print(f'清洗 {sub_skill_md}: 移除 {len(removed)} 处污染')

if __name__ == '__main__':
    main()
```

## 八、最佳实践

### 8.1 开发期

1. **每次优化后立即沉淀** — 不要等"以后再记"，容易遗忘
2. **沉淀要具体** — 写"What"和"Why"，不要只写"改了 xxx"
3. **版本号要准确** — 沉淀记录的版本号要与 SKILL.md 的 version 字段一致
4. **主文档保持纯净** — 写记忆时，检查主文档是否被污染

### 8.2 发布期

1. **发布前必须清洗** — 即使用户没说，也要主动检查
2. **清洗后要验证** — 跑一遍 evals，确保功能未受影响
3. **保留 .dev-memory.md 在本地** — 不要随包发布
4. **生成清洗报告** — 便于追溯和复盘

### 8.3 开源期

1. **开源前全面清洗** — 不仅清洗主文档，还要清洗所有子文档
2. **检查 .gitignore** — 确保 .dev-memory.md 不被提交
3. **检查 artifacts/** — 确保开发期产物不随包发布
4. **README.md 可保留版本历史** — 这是面向用户的正式文档
